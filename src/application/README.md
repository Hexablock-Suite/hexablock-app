Use cases and ports, generic over the variant. It may import only `src/domain/` and other `src/application/` code, and never `src/domain/variants/`.

The aspects of §3.5 live here too. `UseCaseAspect` is the abstract Decorator of `UseCase`, and `LoggingAspect` extends it. The `Logger` port takes a `UseCaseLogEntry`, never a message (decision 37 of the class diagram). `LoggingAspect` is the only writer of the log: no use case takes the `Logger` (#342). `logEntryOf()` copies the field `failedDeliveries` of any success into the entry, so the aspect names no use case and no response type.

`execute()` never throws (decision 28). An aspect puts its concern in `around()` and calls `super.around()` to run the inner use case. `wrapInAspects(useCase, aspects)` in `use-case-aspect.ts` builds a chain of aspects from the outside in: the first aspect sees the call first and the result last (#323). The composition root builds every chain with it. `UseCaseAspect.execute()` turns every exception, from the inner use case or from the aspect's own work, into a failed `Result` with the code `unexpected-failure`, and the `UseCaseError` keeps the exception as its `cause`. `UseCaseError` rejects an empty or blank `code`, and `LoggingAspect` an empty or blank `name`, with a `RangeError`.

`SaveProgress` records a `GameResult` in the `GameProgress` of its game and saves it through the `ProgressRepository` port, the repository of the progress aggregate (#164, decision 57 of the class diagram). It takes the `GameId` of its game and the progress model of the variant in its constructor, and it returns no value. `ProgressRepository` gives back and saves the whole `GameProgress`.

`LoadProgress` reads the saved progress of one game (#181, decision 57 of the class diagram). Its request has no member. It takes the `ProgressRepository` port and the `GameId` of the game in its constructor, as `SaveProgress` does, and it returns the saved `GameProgress` as it is, or `undefined` when the game has none: it writes nothing, and it starts no progress. A port that throws gives a `load-failed` failure. The composition root offers it as `loadProgress(gameId)`, one `LoadProgress` per game over its one local progress repository.

`StartGame` starts a level from its `levelId` (#172, decision 59 of the class diagram). `StartGameRequest` holds an optional `LevelId`, and `StartGame` asks the `GameFactories` port for the `GameFactory` of that level, or of the registered game when the request names no level. A game with no levels starts with no level id. `LevelRepository.levelOf()` gives the definition of one level of a game.

`ListLevels` lists the levels of a game on the chosen figure (#168, decision 58 of the class diagram). Its request holds the `GameId` and the figure as a `TopologyId`. It reads the definitions through the `LevelRepository` port and the progress through `ProgressRepository`, and it returns one `LevelSummary` per level of that figure, in the order of the level files: a `LevelId`, a `LevelStatus` (`completed`, `open` or `locked`) and the `Stars` of a completed level. `LevelStatus` lives in the domain since #326, and its `ofEach()` holds the one rule of a won, open and locked level: the first level is open, and a won level opens the next one, also with zero stars (S3-12 in #151). The use case gives it only the levels of the chosen figure, in order. A figure with no level gives an empty list.

`ListAchievements` lists the achievements of the player with their status (#188, decision 60 of the class diagram). Its request has no member. It gives one `AchievementSummary` per achievement, in the order of the list that the composition root gives: the id of the achievement and whether it is completed. An `Achievement` has an id and an optional `AchievementGoal`, the Strategy that decides when it is completed: `LevelsWon` counts the won levels of one game, and `EveryLevelWon` asks for every level of one game. The goals live in the domain since #326 and call no repository. `ListAchievements` loads the levels through `LevelRepository` and the saved progress through `ProgressRepository` once per game, and passes them to `isReachedBy()` of each goal of that game. A level is won when `LevelStatus.ofEach()` gives it `completed`, the rule of `ListLevels`. An achievement with no goal stays in progress.

`FailureCode` in `result.ts` is the one list of failure codes (#322, decision 62 of the class diagram). A use case builds each error from it, for example `FailureCode.noRunningGame`, and never writes the text of a code: `test/gates/failure-code-gate.test.ts` checks it. A new code goes into this list. The failure codes: `start-failed` (`StartGame`), `no-running-game`, `move-rejected` and `move-failed` (`ApplyMove`), `no-undo`, `nothing-to-undo` and `undo-failed` (`UndoMove`, which also returns `no-running-game`), `nothing-to-redo` and `redo-failed` (`RedoMove`, #178, which also returns `no-running-game`), `save-failed` (`SaveProgress`), `load-failed` (`LoadProgress`, #181), `list-failed` (`ListLevels` and `ListAchievements`), and `unexpected-failure` (`UseCaseAspect`). The engine records its events, and `ApplyMove` delivers them to the `GameEventPublisher` port after the turn (#233). `ApplyMove` answers success with the saved turn when the publisher throws (decision 29). The success carries each failed delivery as a `publish-failed` `UseCaseError` in `MoveResult.failedDeliveries` (#342), and `LoggingAspect` writes them in the one entry of the call.
