Use cases and ports, generic over the variant. It may import only `src/domain/` and other `src/application/` code, and never `src/domain/variants/`.

The aspects of §3.5 live here too. `UseCaseAspect` is the abstract Decorator of `UseCase`, and `LoggingAspect` extends it. The `Logger` port takes a `UseCaseLogEntry`, never a message (decision 37 of the class diagram). `LoggingAspect` is the only writer of the log for a use case: no use case takes the `Logger` (#342). Since #384 `AchievementCounterListener` of layer 3 also writes one `failure` entry with a `save-failed` error for each failed save of the counters. `logEntryOf()` copies the field `failedDeliveries` of any success into the entry, so the aspect names no use case and no response type.

`execute()` never throws (decision 28). An aspect puts its concern in `around()` and calls `super.around()` to run the inner use case. `wrapInAspects(useCase, aspects)` in `use-case-aspect.ts` builds a chain of aspects from the outside in: the first aspect sees the call first and the result last (#323). The composition root builds every chain with it. `UseCaseAspect.execute()` turns every exception, from the inner use case or from the aspect's own work, into a failed `Result` with the code `unexpected-failure`, and the `UseCaseError` keeps the exception as its `cause`. `UseCaseError` rejects an empty or blank `code`, and `LoggingAspect` an empty or blank `name`, with a `RangeError`.

`SaveProgress` records a `GameResult` in the `GameProgress` of its game and saves it through the `ProgressRepository` port, the repository of the progress aggregate (#164, decision 57 of the class diagram). Since #46 it reads the owner with `owner()` and writes through `update()`, which loads, changes and saves the progress in one queue per key (decision 66). It takes the `GameId` of its game and the progress model of the variant in its constructor, and it returns no value. Since #180 the composition root builds it for a finished game with the progress model of its level, and `ResultPresenter` calls it. `MoveResult` carries the optional `moves` and `levelId` of the game (D26): `moveResultOf()` asks the photo for `moveCount()` and the root for `levelOfMatch()`. `ProgressRepository` gives back and saves the whole `GameProgress`.

`LoadProgress` reads the saved progress of one game (#181, decision 57 of the class diagram). Its request holds the `GameId` of the game, as the request of `ListLevels` does (#410). It takes the `ProgressRepository` port in its constructor, and it returns the saved `GameProgress` as it is, or `undefined` when the game has none: it writes nothing, and it starts no progress. A port that throws gives a `load-failed` failure. The composition root builds one `LoadProgress` over its one local progress repository and offers it as `loadProgress()` for every game.
`AchievementCounterRepository` is the port of the counters of the achievements (#363, decision 57 of the class diagram). It gives back and saves the whole `AchievementCounters` of one game, its own aggregate apart from `GameProgress`, with `load(gameId)` and `save(counters)`. `AchievementCounterListener` of layer 3 writes the counters through it, and `ListAchievements` reads them through it (#364).

`StartGame` starts a level from its `levelId` (#172, decision 59 of the class diagram). `StartGameRequest` holds an optional `LevelId`, and `StartGame` asks the `GameFactories` port for the `GameFactory` of that level, or of the registered game when the request names no level. A game with no levels starts with no level id. `LevelRepository.levelOf()` gives the definition of one level of a game. Since #397 `StartGame` refuses a locked level: it takes the `LevelRepository` port, an optional `ProgressRepository`, the `GameId` of its game and its figure in its constructor, gives `LevelStatus.ofEach()` the levels of its figure in the order of `levelsOnFigure()`, the list of `ListLevels`, and returns `level-locked` for a locked level. With no progress repository or no saved progress, only the first level is open.

`ListLevels` lists the levels of a game on the chosen figure (#168, decision 58 of the class diagram). Its request holds the `GameId` and the figure as a `TopologyId`. It reads the definitions through the `LevelRepository` port and the progress through `ProgressRepository`, and it returns one `LevelSummary` per level of that figure, in the order of the level files: a `LevelId`, a `LevelStatus` (`completed`, `open` or `locked`) and the `Stars` of a completed level. `LevelStatus` lives in the domain since #326, and its `ofEach()` holds the one rule of a won, open and locked level: the first level is open, and a won level opens the next one, also with zero stars (S3-12 in #151). The use case gives it only the levels of the chosen figure, in order. A figure with no level gives an empty list. The composition root builds it once and offers it as `listLevels()` to the level selector (#173).

`ListAchievements` lists the achievements of the player with their status (#188, decision 60 of the class diagram). Its request has no member. It gives one `AchievementSummary` per achievement, in the order of the list that the composition root gives: the id of the achievement and whether it is completed. An `Achievement` has an id and an optional `AchievementGoal`, the Strategy that decides when it is completed: `LevelsWon` counts the won levels of one game, `EveryLevelWon` asks for every level of one game, `BestCountReached` asks for a best count of one game, and `TotalCountReached` for a total of one game (#364). The goals live in the domain since #326 and call no repository. `ListAchievements` loads the levels through `LevelRepository`, the saved progress through `ProgressRepository` and the saved counters through `AchievementCounterRepository` once per game, and passes them to `isReachedBy()` of each goal of that game. A game with no saved counters gets new counters, so every goal gets the three data (#406). A level is won when `LevelStatus.ofEach()` gives it `completed`, the rule of `ListLevels`. An achievement with no goal stays in progress; since #364 each registered achievement has a goal.

`FailureCode` in `result.ts` is the one list of failure codes (#322, decision 62 of the class diagram). A use case builds each error from it, for example `FailureCode.noRunningGame`, and never writes the text of a code: `test/gates/failure-code-gate.test.ts` checks it. A new code goes into this list. The failure codes: `start-failed` (`StartGame`), `no-running-game`, `move-rejected` and `move-failed` (`ApplyMove`), `no-undo`, `nothing-to-undo` and `undo-failed` (`UndoMove`, which also returns `no-running-game`), `nothing-to-redo` and `redo-failed` (`RedoMove`, #178, which also returns `no-running-game`), `save-failed` (`SaveProgress`), `load-failed` (`LoadProgress`, #181), `list-failed` (`ListLevels` and `ListAchievements`), `level-locked` (`StartGame`, #397), `username-taken`, `wrong-credentials`, `invalid-credentials` and `backend-unreachable` (`Register` and `Login`, from an `AccountFailure` of the gateway, #45), `sign-in-after-sign-up-failed` (`Register`, from an `AccountFailure` of the gateway when the sign-in after a sign-up fails), `register-failed` (`Register`), `login-failed` (`Login`), `session-expired` (`SyncProgress`, from a `SyncFailure` of the gateway, which also gives `backend-unreachable`, #46), `sync-failed` (`SyncProgress`), and `unexpected-failure` (`UseCaseAspect`). The engine records its events, the events of each move (#361) and the `GameEnded` of the last turn, and `ApplyMove` delivers them to the `GameEventPublisher` port after the turn (#233). `ApplyMove` does not know the class of an event. `ApplyMove` answers success with the saved turn when the publisher throws (decision 29). The success carries each failed delivery as a `publish-failed` `UseCaseError` in `MoveResult.failedDeliveries` (#342), and `LoggingAspect` writes them in the one entry of the call.

`Register` and `Login` sign the player up and in (APP-FR-12, #45, decision 65 of the class diagram). Each one implements `UseCase<Credentials, Session>`: `Credentials` holds the username and the password of the form, and `Session` is the value object with the bearer token and the user id of the account. Each one asks its operation of the `AccountGateway` port for the session and writes it through the `SessionStore` port, with the one function `keptSession()` of `account-gateway.ts`. A known failure of the gateway is an `AccountFailure` with its code. Any other failure gives `register-failed` or `login-failed`, and a failure of the gateway writes no session. With an `AnonymousMerge`, `keptSession()` then merges the progress played with no account into the new user. `SyncProgress` reads the session through `SessionStore.read()`. `SessionStore.owner()` gives the owner of the progress, the last signed-in user, and `SessionStore.clear()` forgets the token and keeps that owner when the backend refuses the token (#46).

`SyncProgress` sends the local progress of one game to the backend (APP-FR-13, D27, #46, decision 66 of the class diagram). Its request holds the `GameId`. It reads the session once through `SessionStore`; with no session it sends nothing and succeeds, so `SaveProgress` and `ListLevels` still need no session. A session that cannot be read gives `sync-failed` and writes nothing. With a session, its user is the owner (`ProgressOwner`) for the whole sync. It merges the anonymous progress into that owner through `AnonymousProgress.mergeAnonymousInto()`, loads the progress of the owner, sends it through the `ProgressGateway` port outside the queue of the repository, and merges the answer of the backend with `mergeWith()` (DS-12) through `ProgressRepository.update()` into the progress stored at that moment. A game with no local progress sends nothing. A failed sync never loses local progress. A known failure of the gateway is a `SyncFailure` with its code, `session-expired` or `backend-unreachable`, and `session-expired` also clears the token and keeps the owner. Any other failure gives `sync-failed`. `ResultPresenter` calls it after each save, and `AccountPresenter` after each sign-in, for each registered game. `SaveProgress` and the readers read the owner once per call through `ProgressRepository.owner()`.
