Interface adapters (presenters, view models, mappers, repository implementations). It may import `src/application/` and `src/domain/`.

Today it holds `InMemoryGameRepository`, the adapter of the `GameRepository` port, and `NullGameEventPublisher`, a `GameEventPublisher` that does nothing until `GameEventBus` exists. Each adapter runs the contract suite of its port in `test/support/contracts/`, the same suite as the test fake.

`HomePresenter` is the MVP presenter of the home screen and of the game selector map (#169). It takes the ids of the registered games and the texts of one language, and it imports no React. It finds the texts of each game under `game.<id>.name` and `game.<id>.place` in the catalog.

`key-value-store.ts` holds `KeyValueStore`, the driver interface of the local storage (issue #155). It keeps one text value for each text key. The local repositories of this layer use it, and `DeviceKeyValueStore` in `src/infrastructure/` implements it, so no adapter imports a storage package. `InMemoryKeyValueStore` in `test/support/adapters/` is its test fake, for the integration tests of APP-NFR-15.

`LocalProgressRepository` is the adapter of the `ProgressRepository` port over `KeyValueStore` (#164, decision 55 of the class diagram). It keeps the `GameProgress` of each game as one JSON text of plain numbers and texts under the key `progress:<game id>`, with a `version` field. It reads each value of the domain with `deliverTo(receiver)` (rule R-no-delivery-call), and it builds a loaded progress again with `GameProgress.start()`, `recordScore()` and `recordLevel()`. A saved progress that it cannot read throws, and it never writes over it. It runs the contract suite of its port in `test/support/contracts/`.

It also holds the bundled level files in `levels/<game>/` (issues #166 and #167, A6): one JSON file per hand-made level, in the shared level format of hexablock-api `docs/level-format.md`. `levels/fit/` holds the first Fit levels, and `fit-01.json` is the complete Fit example of that document. `levels/sort/` holds the first Sort levels, and `sort-01.json` is the complete Sort example of that document. Each Sort level picks its piece source (A4): `sort-01` draws from a seed, and `sort-02` and `sort-03` give a fixed list of stacks. `BundledLevelRepository` implements the `LevelRepository` port over them (#168, decision 56 of the class diagram): it imports each file as a JSON module, so the device needs no file system, and it gives the levels whose `gameId` names the asked game. A new level file adds one import to it, and its test reads the folders, so a file that it misses fails the test. A level file is plain data, and an adapter turns it into a `LevelDefinition` of the engine (classes.md decision 24).

It also holds the typed text catalog in `texts/` (APP-FR-11, issue #154). `es.ts` and `en.ts` hold one Spanish and one English entry for each key, and `text-catalog.ts` joins them. A screen shows a text through its key, never through a literal text (rule R-text-catalog in `AGENTS.md`).
