# Requirements

This file is the team's working copy of the project requirements, written in our own words. It is the canonical requirements document for both repositories; `hexablock-api/docs/REQUIREMENTS.md` holds the backend view and links here.

- **Source:** the course statement "Proyecto Semestral — HexaBlock Suite", version 1.0, issued 2026-10-23. It is not redistributed in this repository. Each item cites its section as `§n`.
- **Status words:** **Required** comes from the statement. **Derived** is not in the statement, but a statement item needs it. **A#** is an assumption we work under until the professor answers. **D#** is a team design decision. **Q#** is an open question for the professor. **C#** is a confirmation we will ask for, but it does not block work.
- **Requirement IDs:** **APP-FR-n** is a functional requirement: what the app does for the player. **APP-NFR-n** is a non-functional requirement: how the app is built, tested and documented. The backend uses API-FR-n and API-NFR-n. An ID never changes; a dropped requirement keeps its ID and says "Dropped".
- **Checks:** each requirement ends with _Check_, the evidence that shows it is met. Where a gate already exists, the check names it. The other checks are a proposal of 2026-10-30 for the team to review.
- **Rule:** when a requirement, an assumption or an answer from the professor changes, update this file in the same pull request.

## 1. Product

One mobile app with four puzzle games on hexagonal boards, built on one generic engine, plus a REST backend (§2). The grade measures the engine, not the four games: four modules that repeat the board, rendering, persistence or game flow are graded as insufficient even if they work (§2).

## 2. Generic engine (non-functional, §3.1)

- **APP-NFR-01 — Generic board (§3.1).** A hexagonal board generic over the cell type, in axial coordinates (q, r), with configurable shape, neighbors, axis traversal and rotation. It is written once and used by all four variants. The gate `test/gates/one-board-gate.test.ts` has one known gap, which the team accepts (gap G112.1): it catches a class whose name ends with `Board` and a class that extends `Board`, but not a class with another name that keeps the cells in a `Map`. The net is the type of `board`: when a variant state keeps such a class in `board`, the gate reports the member type, and `pnpm typecheck` fails, because the runtime checks of the gate assign each state's `board` to a variable typed as the engine `Board`. _Check:_ the four variants use the same board class with a different cell type, and no variant has a board class of its own.
- **APP-NFR-02 — Generic rules contract (§3.1).** A rules contract generic over cell, move and state: valid moves, apply a move, run the resolution rule, evaluate the end of the game. Each variant implements it. _Check:_ each variant's rules class implements the contract, and the engine calls only the contract.
- **APP-NFR-03 — Generic game engine (§3.1).** A game engine generic over cell, move and state that runs the turn cycle (start, receive, validate, apply, resolve, evaluate, notify). It knows no variant and no UI framework. _Check:_ `pnpm arch` passes rules `engine-no-variants` and `domain-no-framework`, and the engine test of APP-NFR-13 runs with a fake cell type.
- **APP-NFR-04 — Interchangeable sources and policies (§3.1).** Abstractions for the piece source (seeded random generator or fixed list per level), the scoring policy and the progress model (high score or levels with stars), all interchangeable. _Check:_ a test swaps each implementation and the engine code does not change.
- **APP-NFR-05 — Bounded generics (§3.1).** Bounded generics where the engine needs a capability of the cell content (for example a mergeable bound for Hexa Merge). The README explains why each bound exists. _Check:_ the README section "Generic Engine" lists every bound with its reason.
- **APP-NFR-06 — Extensibility proof (§3.1).** `docs/EXTENSIBILITY.md` explains, step by step with real class names, which files a fifth variant adds and which files it does **not** touch. In the defense the jury proposes a small rule change (board size, scoring policy or piece shape) and the change must stay in new classes or configuration. _Check:_ before the defense we apply each of the three example changes on a branch, and the diff touches no engine file.
- **APP-NFR-07 — Reproducible randomness (§1.4, §3.6).** Random generation is injectable and reproducible with a seed, so a game can be tested deterministically. _Check:_ gate `test/gates/domain-purity-gate.test.ts` (rule R-domain-determinism in `AGENTS.md`), and a Merge test with a fixed seed always gets the same new tiles.

## 3. Principles, patterns and architecture (non-functional)

- **APP-NFR-08 — SOLID (§3.2).** Every principle used is documented in the README with a concrete example from our code. The engine has no conditionals on the variant type (LSP). Undo, timing and seeded randomness are separate interfaces, so Hexa Lines does not implement undo (ISP). _Check:_ the README section "SOLID Principles" has one example per principle with a link to its file, and the engine has no `if`, `switch`, ternary, `&&`, `||`, `??` or table lookup on the game id (gate `test/gates/engine-game-id-gate.test.ts`, rule R-engine-no-game-id in `AGENTS.md`).
- **APP-NFR-09 — GoF patterns (§3.3).** Strategy and Abstract Factory (one factory per variant) are mandatory. The statement also lists Builder, Singleton or single-scope injection, Prototype, Composite, Decorator, Adapter, Facade, Observer, Command, State, Template Method and Iterator. Each pattern used has a justification, a code excerpt and a README entry. See D7. _Check:_ the README section "Design Patterns" lists each pattern used with its justification and a link to its file, and Strategy and Abstract Factory are in it.
- **APP-NFR-10 — Clean Architecture (§3.4).** Four layers with dependencies pointing inward. The whole generic engine and the variant rules live in the entities layer with no external dependency. Use cases are generic, never one copy per game. A layer diagram is an image in the README and an editable source in the repo. In the session of 2026-11-03 the professor named the valid hybrid: Clean plus an architecture made for games, not Hexagonal plus Clean: «no, no, entre hexagonal y clean, perdón, entre clean y alguna arquitectura particular para juegos». A layered architecture that is not Clean is also valid when the team cites its reference and documents it. Every part of the app follows the layers, the presentation layer included: «la arquitectura a todo nivel de tu aplicación». Each layer has a defined meaning and keeps the dependency rule. _Check:_ `pnpm arch` passes, and [`architecture/layers.md`](architecture/layers.md) holds the layer diagram.
- **APP-NFR-11 — AOP (§3.5).** At least one cross-cutting aspect (logging, centralized errors with retry, profiling, authorization or caching), built as decorators or proxies over the use cases. One aspect on the generic use case covers all four variants. See A2. _Check:_ a test shows that one aspect runs for the four variants, and the use case it wraps has no line of the aspect's code.
- **APP-NFR-25 — Justified primitive types (professor guidance).** The primitive types in the design tend to zero, and each primitive that stays has a written reason. A `boolean` needs no reason. A closed union or a value object replaces a primitive where the domain allows it: For example, `line('nort', …)` does not compile, and `Radius.of(-1.5)` throws a `RangeError`. Source: the professor's guidance, per Oscar's account of 2026-11-05; the exact wording and the session are not recorded yet. Issue [#86](https://github.com/Hexablock-Suite/hexablock-app/issues/86). _Check:_ gate `test/docs/primitive-types.test.ts` lists every `number` and `string` in the public signatures of `src/domain/engine/` and fails when one has no row, with its reason, in the README table «Primitive types».

## 4. Tests (non-functional, §3.6)

- **APP-NFR-12 — Unit tests.** Statement §3.6 asks for unit tests of the entities, the use cases and the services. We test their behavior through the public interface of the engine and of the use cases, not one test file per class: a test per class ties the tests to the class structure, so every refactor breaks them. Test doubles replace only the boundaries: the ports of layer 2 and the engine interfaces that an outer layer implements (`Clock`, `RandomSource`, `GameEventPublisher`). The team accepts one exception (gap G113.2): the rules suites of Lines, Sort and Merge pass an `IScoringPolicy` double that gives no points, because a rules suite tests the rules, and the scoring of each variant has its own suites. Each variant's rules have their own suite (lines on 3 axes, exact cover, cascade transfer, merge on collision). _Check:_ `pnpm test` runs them in CI, with one rules suite per variant, and no test replaces an engine or variant class with a double.
- **APP-NFR-13 — Engine without a variant.** The engine is tested with a fake cell type, to show it depends on no variant. _Check:_ an engine test uses a cell type and a square topology that exist only in the tests (D4).
- **APP-NFR-14 — Test doubles and style.** Mocks or stubs for repositories, network and a fixed-seed random source; Arrange-Act-Assert; names `should_[result]_when_[condition]`; tests check behavior, not implementation details. _Check:_ gate `test/gates/test-title-gate.test.ts` (rule R-test-names).
- **APP-NFR-15 — Integration tests.** Use cases with real repositories on an in-memory database; save and load progress per variant end to end. _Check:_ one integration test per variant saves progress and loads it back.
- **APP-NFR-16 — Widget and UI tests.** Rendering, interaction, and navigation between home, game selector, level selector, game, victory and defeat. _Check:_ a navigation test visits the six screens.
- **APP-NFR-17 — Contract tests.** Contract tests with Pact (recommended). _Check:_ `pnpm pact:check` passes, and `pacts/` is committed.
- **APP-NFR-18 — CI.** CI runs the tests on every pull request. _Check:_ the `verify` job of `.github/workflows/` runs on every pull request.

The rows «Square cells instead of hexagons» and «Triangular cells» of the [variation register](#8-variation-register) declare the two new figures. ## 6. Backend features, client side (functional, §5.2)

The backend requirements live in `hexablock-api/docs/REQUIREMENTS.md`, as API-FR-01 to API-FR-06. In short: sign-up and sign-in with JWT; progress sync with `gameId` as a required key (one entry per user and variant); a global leaderboard per `gameId` and, for level-based variants, per level; read and update level definitions for Fit and Sort with one generic schema plus a section per `gameId`; Swagger/OpenAPI; consistent HTTP errors.

On 2026-10-30 the team closed two shapes of this contract. The detail is in `hexablock-api/docs/REQUIREMENTS.md` §4, under DS-5 and DS-6:

- **DS-5 — Progress shape.** One progress row per user and `gameId`, plus a level results table. The app sends a level result as `stars`, `moves` and `elapsedMs`, the field names of `GameResult`. In the backend domain, `PlayerProgress` is the aggregate root and keeps its level results; one repository saves both tables.
- **DS-6 — Level schema.** A common part (`gameId`, `levelId`, `order`, `version`, `topology`) plus a typed section per `gameId`. The Fit section holds `figure`, `pieces` and `witness`. The Sort section holds `radius`, `goals` and `source`. The Fit check reads the rotation steps from the topology that the `topology` field names, so the API accepts a level of any topology that the code knows; it does not reject a topology only because it is not hexagonal (A5).

On 2026-11-06 the team closed two sync rules. The detail is in `hexablock-api/docs/REQUIREMENTS.md` §4, under DS-11 and DS-12:

- **DS-11 — Level version.** The app can hold a bundled copy and a backend copy of one level, with the same `gameId` and `levelId`. The copy with the higher `version` wins. When the versions are equal, the app uses the bundled copy. A `levelId` that only the backend has adds a level.
- **DS-12 — Best result per level.** When one account sends two results for one level, the backend keeps the best one. DS-4 decides which result is the best. The high score follows the same rule: the highest one stays. So the order of the syncs does not change the stored progress.

On 2026-10-31 the backend moved its `Clock` port to the application layer (API-NFR-11): `src/application` reads the time from the `Clock` port in `src/application/ports/clock.ts` and passes the instant to `src/domain` as a parameter, because ports live in the application layer and the domain never imports it.

DS-4, what orders the per-level leaderboard, is still open (§10, "Still to define").

The app needs its own side of these features. Statement §5.1 does not list them, so each one is **Derived** from the backend item it serves.

- **APP-FR-12 — Account (derived from §5.2.1).** The player can sign up and sign in from the app, and the app keeps the session for the next requests. _Check:_ after sign-in, a sync request carries the token.
- **APP-FR-13 — Progress sync (derived from §5.2.2).** The app sends the local progress of each variant to the backend. When two results of one level arrive, the backend keeps the best one (DS-12). _Check:_ progress saved in the app appears in the backend entry for that user and `gameId`.
- **APP-FR-14 — Leaderboard (derived from §5.2.3).** The app shows the global leaderboard per variant and, for Fit and Sort, per level. Assumption: §5.1 lists no leaderboard screen, so its place in the app is ours to choose. _Check:_ a UI test shows both leaderboards from a stubbed API.
- **APP-FR-15 — Levels from the backend (derived from §5.2.4, A6).** Bundled levels always work offline; levels from the backend add to them or replace them. When both copies of one level exist, the copy with the higher `version` wins (DS-11). _Check:_ with the network off, every bundled level opens; with a bundled copy and a backend copy of one level, the copy with the higher `version` loads.

## 7. Documentation and deliverables (non-functional)

- **APP-NFR-19 — Diagrams (§4).** Class diagram (generic types in UML template notation, layers, patterns), Clean layer diagram (ports and adapters), extensibility diagram (engine in the center, variants as extensions, and the extension points that a fifth variant implements). Each one is a high-resolution image in the README and an editable source in `docs/`. In class on 2026-10-26 the professor asked for the class diagram to model the architecture: it shows which layer each class lives in, and its relations between layers follow the dependency rule. He does not want an entity-relationship diagram. In the class and the consultation of 2026-10-30 he added two rules. A type that a class only receives as a parameter is a dependency. A domain builder builds the logical structure and nothing more, so an adapter reads each level file and the builder gets plain data. In the class of 2026-11-02 he corrected the notation. He asked for explicit dependencies (use, extend, implement) between layers, and for a diamond only where it is needed, such as an entity that holds a Strategy. Every relation between two layers is a dependency, also when the class keeps the other class as an attribute. A diamond (aggregation or composition) stays only inside one layer, and only where it makes a GoF pattern visible: «Aquí sí porque quiero hacer visible el patrón estratégico». Any other attribute, a domain relation included, is a use with the attribute name and its multiplicity, because the class box already shows the attribute. In the same class he asked every use case to show its operation with its parameters, and an output port to take a typed object instead of a prebuilt message, so the adapter writes the text. The class diagram follows these rules (decisions 23, 24 and 37 in [`architecture/classes.md`](architecture/classes.md)). _Check:_ the README embeds the three images; [`architecture/layers.md`](architecture/layers.md), [`architecture/classes.md`](architecture/classes.md) and [`architecture/extensibility.md`](architecture/extensibility.md) hold the three sources.

## 9. Assumptions

Each assumption holds under both readings of the statement, or names what changes if the answer differs.

- **A1 — Merge cell (§3.1).** The statement says the Merge cell is an integer and also that it carries a mergeable bound. A primitive integer cannot implement an interface, so the Merge cell is a value object that wraps an integer and implements the bound. It satisfies both sentences; the statement calls its names "orientativos". Confirmation C2.
- **A2 — Aspects (§3.5).** Aspects are our own decorators or proxies over the generic use case, not a library or framework interceptor. This holds whether libraries are allowed or not. Confirmation C5.
- **A3 — End of Merge (§1.4, §5.1.4).** Reaching the target tile is an event, not the end of the game; an end policy decides. Default: a victory screen with a "continue" option, as in 2048. Confirmation C3. Confirmed on 2026-11-03: the player may continue to get more points (C3).
- **A4 — Sort pieces (§1.3, §1.5, §5.1.5).** Each Sort level chooses its piece source: seeded random or a fixed list. Default: seeded random per level, so a level is reproducible and can be designed. Confirmation C4.
- **A5 — Fit levels can be won (§1.2, §5.2.4).** The Fit illustration shows a figure of 21 cells and pieces of 20, against the rule that both areas are equal. We read it as a hint: every Fit level must be provably winnable. Equal area is necessary but not enough, and finding an exact cover is a search problem. So every level file carries the designer's solution (piece, rotation, position). The rotation counts steps of the level's topology, never degrees: the hexagonal topology has six steps of 60°, and another topology gives its own steps (D4). Checking that witness is linear. The Fit Builder checks area and witness when a level loads, a CI test checks every bundled level, and the backend rejects a level whose witness fails. A search tool only helps level designers. Pieces rotate; they are never mirrored (§1.2 mentions rotation only). Confirmations C1 and C7. The rotation rule is confirmed on 2026-11-03 (C7).
- **A6 — Level origin (§5.1.5, §5.2.4).** Levels bundled in the app always work offline; levels from the backend add to them or replace them. Who may edit levels is Q4, answered on 2026-11-03. When the app and the backend hold the same level, DS-11 decides which copy wins (2026-11-06).
- **A7 — Public repositories (§2, §9).** Both repositories are public, because GitHub Free protects branches only on public repositories. Confirmation C6.
- **A8 — Delivery date.** We plan against the earliest date, 2026-12-07. See Q1.
- **A9 — Backend scope (§6.1).** Replaced by D6 on 2026-10-26.
- **A10 — Patterns (§3.3).** Replaced by D7 on 2026-10-26.

## 10. Team design decisions

- **D1 — Turn ownership (§3.1, §3.3, §3.4).** The game engine holds the turn skeleton (Template Method). Each variant supplies the steps through the rules contract (Strategy). The apply-move use case only loads, persists and carries the aspects. Amended by D13 on 2026-10-30: the turn skeleton lives in an abstract base class of the rules contract.
- **D2 — States (§3.3).** Game lifecycle states (playing, resolving, paused, game over, victory) live in the domain. The menu belongs to the presentation layer.
- **D3 — Rendering (§1.5).** A shared board renderer draws the grid and delegates each cell to a cell renderer per variant (Strategy), which the variant's factory provides. The piece preview is a clone (Prototype). Visitor fits only inside the piece and figure Composite, where the node types are closed (cell and region) and the operations grow (area, bounds, rotation). A Visitor over variants would force every new variant to edit all visitors, which breaks the extensibility test.
- **D4 — Grid topology.** Neighbors, slide directions, line axes, rotation step, coordinates and screen layout live behind one topology interface. Rules ask the topology and never hard-code 6 directions, 3 axes or 60°. A minimal square topology used in engine tests proves the engine does not depend on hexagons.
- **D5 — Seams for named variations.** Every axis in §8 gets its seam when the part it touches is built, never on the last day. A late request from the professor must then mean new classes or a new adapter, not a rewrite. This is deliberate insurance: we accept some extra abstraction, as long as each one keeps a written reason (a row in §8 or a layer boundary).
- **D6 — Backend scope (§6.1).** The backend meets the same standards as the client: generics, SOLID, Clean Architecture, the patterns it needs (D7), `EXTENSIBILITY.md` and its own diagrams. Decided by the team on 2026-10-26; it closes Q2 and replaces A9.
- **D7 — Patterns (§3.3).** Strategy and Abstract Factory are mandatory. We use the other listed patterns only where the design needs them, and each one has a written justification. We bring the patterns we identify to the professor as design questions (§11). Decided by the team on 2026-10-26; it closes Q3 and replaces A10.
- **D8 — Variants delivered (§8).** Three games are the minimum (class on 2026-10-26). We deliver the four variants of the statement. Decided by the team on 2026-10-26; it closes Q5.
- **D9 — Builders (§3.3).** A builder builds an object made of parts, step by step: each step returns the builder, and only `build()` returns the product. A record of plain fields gets no builder. The level builders of Fit and Sort stay, because each one builds a level of parts. `FitLevelBuilder` adds the header, the figure, the pieces and the witness. `SortLevelBuilder` adds the header, asks `BoardBuilder` for the board region of the level radius, and adds the goals and the piece source. A `BoardBuilder` in layer 1 builds the board too. It is the DDD factory of the board: it builds the logical structure and nothing more (class on 2026-10-30). In DDD terms, this builder is the factory of the board. Its reasons: two construction paths (a region by radius for Lines, Sort and Merge; a figure for Fit, §1.2), the topology rows of §8 (D4) and the generic coordinate of D10. Decided by the team on 2026-10-30. Rewritten on 2026-10-31: `SortLevelBuilder` now builds the level step by step, because a builder for a flat record of four fields has no parts to assemble. See decision 15 in [`architecture/classes.md`](architecture/classes.md).
- **D10 — Generic engine names (§3.1, §8).** The engine names carry no geometry: `Board<TCell, TCoord, TAxis>` and `GridTopology<TCoord, TAxis, TDirection>`. `TAxis` and `TDirection` are the closed name unions of one topology (APP-NFR-25). `HexCoord` and `HexTopology` are the hexagonal implementation. `Board` is the `HexBoard<TCell>` of §3.1, which calls its names «orientativos». The variant classes drop the `Hexa` prefix, and «Hexa Lines» and the others stay as display names. A triangular or 3D board is one more coordinate type and one more topology. In class on 2026-10-30 the professor asked for one generic board for hexagons, triangles and squares. Decided by the team on 2026-10-30. See decision 16 in [`architecture/classes.md`](architecture/classes.md).
- **D11 — Geometry family (§3.3, §8).** An Abstract Factory of geometry in layer 1 creates the coordinate, the topology and the piece shapes of one geometry: hexagonal (the real one) and square (the engine tests, D4 and APP-NFR-13). The board builder, the level builders and each variant factory receive it by composition, so no class exists per game and geometry. Screen layout per geometry stays in the presentation layer. Decided by the team on 2026-10-30. See decision 17 in [`architecture/classes.md`](architecture/classes.md) and view 3 of [`architecture/extensibility.md`](architecture/extensibility.md).
- **D12 — Single scope (§3.3).** §3.3 names «Singleton (o inyección de dependencias con alcance único)». The composition root creates `AudioManager` and `SessionManager` once and injects them. No class has a static `instance()`. `AudioManager` stays the audio Facade. Decided by the team on 2026-10-30. See decision 18 in [`architecture/classes.md`](architecture/classes.md).
- **D13 — Template Method in an abstract base class (§3.3).** It amends D1. The abstract `BaseGameRules` implements the rules contract and holds the template method `playTurn()` over abstract steps. Each variant extends it. The game engine depends only on the rules contract, so Strategy stays. Decided by the team on 2026-10-30. See decision 21 in [`architecture/classes.md`](architecture/classes.md).
- **D14 — Pattern audit (§3.3).** The fourteen patterns of §3.3 all stay. `TimedRulesDecorator` wraps the rules contract and times the game, because Fit stars use time (§1.2). State keeps D2: no `MenuState`, because the menu is navigation in the presentation layer. Decided by the team on 2026-10-30. See decisions 19 and 20 in [`architecture/classes.md`](architecture/classes.md).
- **D15 — Open game id (§3.1, APP-NFR-06).** The game id is an open value object over a validated string, not a closed list of the four games. Each variant factory declares its own id. So a fifth variant changes no engine file, and only the composition root and the game selector list the games. Proposed on 2026-10-31 for team review. See decision 30 in [`architecture/classes.md`](architecture/classes.md) and [`EXTENSIBILITY.md`](EXTENSIBILITY.md).
- **D16 — Piece source as Iterator (§3.1, §3.3).** The piece source contract is a Strategy and an Iterator: it adds `[Symbol.iterator]()` next to `hasNext()` and `next()`. The seeded source never ends, and the fixed list of Fit ends. Decided by the team on 2026-11-01. See decision 32 in [`architecture/classes.md`](architecture/classes.md).
- **D17 — Valid moves (§3.1).** The rules contract gains `validMoves(state): Iterable<TMove>`, a lazy generator, because §3.1 says the rules «define los movimientos válidos». The «no valid move» end of Lines, Sort and Merge stops at the first move. Decided by the team on 2026-11-01. See decision 33 in [`architecture/classes.md`](architecture/classes.md).
- **D18 — Memento in undo (§3.3, §5.1.8).** `MoveCommand.before` is the Memento: the engine is the originator, the cloned state is the memento and `MoveHistory` is the caretaker. Decided by the team on 2026-11-01. See decision 34 in [`architecture/classes.md`](architecture/classes.md).
- **D19 — No Visitor, no Mediator (§3.3).** Visitor is discarded with the reasoning of D3, and no class implements it. `GameEventBus` is an Observer, not a Mediator. Decided by the team on 2026-11-01. See decision 35 in [`architecture/classes.md`](architecture/classes.md).
- **D20 — Composite only for shapes; stars as data (§1.2, §3.3).** Composite stays in the piece and figure shapes only. Fit stars are two thresholds per star (moves and time) in the level file, which `FitLevelBuilder` reads. Decided by the team on 2026-11-01. See decision 36 in [`architecture/classes.md`](architecture/classes.md).
- **D21 — Hexa Sort rules (§1.3).** The proposal of [#56](https://github.com/Hexablock-Suite/hexablock-app/issues/56) is accepted with one change to the tie-break. The whole top run of the color moves, and the amount compared is the size of that top run. A top run of 10 or more removes the whole stack, tiles of other colors below included, and counts one goal (§1.3, «se elimina la pila»). When two stacks have top runs of the same size, the stack whose coordinate key comes first wins. The keys are the topology keys of the board, compared in plain string order (code units), so the result never depends on when a cell was filled or emptied. The proposal broke the tie by the first stack in `board.cells()` order. A cleared cell keeps its old place in that order, so the result depended on the history of the cell (gap G108.3). Accepted on 2026-11-06. `SortRules` (#93) codes these rules.

### Still to define (team)

- Merge: merge order inside one slide, and whether a tile merges once per move; probability of a 2 versus a 4; whether undo restores the random state or regenerates the new tile.
- Lines: whether a combo counts lines on several axes; what a streak is. The code of [#91](https://github.com/Hexablock-Suite/hexablock-app/issues/91) follows the proposal on [#58](https://github.com/Hexablock-Suite/hexablock-app/issues/58), «Propuesta, pendiente del equipo»: the combo is the count of distinct full lines on any axis of the topology after one placement, and the rules clear their union, so a shared cell clears once; a streak is the count of placements in a row that clear at least one line, and the first placement that clears none sets it back to 0. The rules also assume that the tray fills again with the next 3 pieces of the source when its last piece is placed.
- Scoring per variant (§5.1.6) and what orders the per-level leaderboard for Fit and Sort (DS-4); whether undo and remove count as moves for Fit stars. The scoring of [#97](https://github.com/Hexablock-Suite/hexablock-app/issues/97) follows the proposal on [#59](https://github.com/Hexablock-Suite/hexablock-app/issues/59), «Propuesta, pendiente del equipo»: Lines gives 1 point per placed cell and 10 per cleared line, and `ComboMultiplierDecorator` multiplies the line bonus by `lines + streak - 1`; Merge gives the sum of the values that the merges of a slide make, and the new tile adds nothing. Proposal of issue #59, pending the team («Propuesta, pendiente del equipo», 2026-11-06), which `SortScoring` and `FitScoring` (#98) code against: Sort gives 10 points per tile of each stack that the turn clears, and has no stars; Fit gives no points per turn, and a star needs both of its thresholds, the moves and the time (`fitStars`). The leaderboard order (DS-4) and the Fit moves (#60) stay open.
