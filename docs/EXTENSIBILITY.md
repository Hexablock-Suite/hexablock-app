# Extensibility

This page explains how to add a fifth variant. The example is Hexa Fill, the game that statement §3.1 names («por ejemplo, Hexa Fill: pintar celdas con restricciones»). Its rules are not designed yet, so every `Fill` name below is a placeholder.

The steps follow the [class diagram](architecture/classes.md) and the [extensibility diagram](architecture/extensibility.md). The engine, the four variants and the first use cases exist in `src/`. The composition root and its game registry exist too (#162), and so do the home screen, the game selector map and `HomePresenter` (#169), and the figure selector of the home screen (#171). The other classes of layers 3 and 4 that the steps name exist too: the state mappers in `src/adapters/`, the cell renderers in `src/infrastructure/board/`, and the move controls [`LinesControls`](../src/infrastructure/ui/lines-controls.tsx), [`FitControls`](../src/infrastructure/ui/fit-controls.tsx), [`SortControls`](../src/infrastructure/ui/sort-controls.tsx) and [`MergeControls`](../src/infrastructure/ui/merge-controls.tsx) in `src/infrastructure/ui/` (#174 to #177). The domain classes that the steps name exist: the progress models `HighScoreProgress` and `LevelProgress` in [`progress-model.ts`](../src/domain/progress/progress-model.ts), and [`RedoableHistory`](../src/domain/engine/redoable-history.ts), which `FitFactory` picks.

## The rule

A new variant adds classes and data. It changes no engine file, no other variant, no use case and no presenter (APP-NFR-06). Three things make this possible:

- The engine depends only on its contracts: `IVariantFactory`, `IGameRules`, `IScoringPolicy`, `IPieceSource`, `IProgressModel` and `BoardState`. It never names a variant (rule `engine-no-variants`).
- [`GameFactory`](../src/domain/engine/game-factory.ts) puts a game together for every variant (decision 40). It asks its `MatchIdGenerator` for the id of the match, builds the local ids of the first state and of its board from it (decision 52), and asks the variant factory for the parts. So a new variant writes no assembly code and creates no id of a match, a state or a board.
- `GameId` is open. It is a value object over a validated string, not a closed list of four games, and each variant factory declares its own id (D15, decision 30). So the new id needs no change in the engine.

## Steps

1. Create the folder `src/domain/variants/hexa-fill/`. Rule `variants-isolated` lets it import only `src/domain/engine/` and its own files.
2. Write the three type arguments: the cell `FillCell` (`TCell`), the move `FillMove` (`TMove`) and the state `FillState<TCoord>` (`TState`), which implements [`BoardState<FillCell, TCoord>`](../src/domain/engine/board-state.ts). A class that names the coordinate type `TCoord` declares it, so the variant runs on any geometry. The state is an entity inside the `GameEngine` aggregate (decisions 7 and 26), so `FillState` follows the same rules as the four states of the code:
   - **Identity.** Its constructor takes its own [`GameStateId`](../src/domain/engine/game-state-id.ts), the [`MatchId`](../src/domain/engine/match-id.ts) of its game and its board. `equals()` compares the `GameStateId` only, and `belongsTo(match)` compares the `MatchId`. `clone()` keeps both ids.
   - **Private fields.** No other class reads or writes a field of the state.
   - **Business methods.** The state changes in place, only through its own methods with business names. Each one returns nothing, and a refused input throws a `RangeError` and leaves the state as it was. `addPoints(points: Score)` adds the points of a turn, and the state keeps its score as a [`Score`](../src/domain/shared/score.ts).
   - **The photo.** `snapshot()` returns a frozen `FillSnapshot`, which extends the abstract class `BoardSnapshot<FillCell, TCoord>` with the data of the variant in private fields, answers a query with a business name for each datum that the rules, the scoring or `restore()` read, and implements `view()`. The view is the data for the screen (decision 29): its fields are private too, and `deliverTo(receiver)` gives them to a receiver of the edge (decision 7). `restore(snapshot)` takes a photo of the same state back in place, and calls `checkOwnSnapshot()` before it writes anything.
   - **The gate.** `test/gates/state-writes-gate.test.ts` reads the new state file too (rule R-state-writes in `AGENTS.md`).
3. Write the rules: `FillRules` extends `BaseGameRules<FillMove, FillState>` and implements the steps `isValid()`, `apply()`, `resolve()` and `evaluate()`, plus `validMoves()`, the lazy generator of the valid moves (decision 33). The rules read the photo of the state and ask the state queries with business names. They change the state only through its business methods, and `apply()` returns the state that it receives. When Hexa Fill has several kinds of move, each move class holds its own check and its own change, as the Fit moves do with `isValidOn()` and `applyTo()` (decision 43). The rules ask the move and never tell the moves apart by their class, so a new kind of move adds a class. The template method `playTurn()` stays in the engine (D13).
4. Write the scoring policy: `FillScoring` implements `IScoringPolicy<FillState>`. Its `score(before, after)` reads two photos of the state, `SnapshotOf<FillState>`, and returns the points of the turn as a `Score`, a safe integer of 0 or more. A bonus is a subclass of `ScoringDecorator`.
5. Write the factory: `FillFactory<TCoord>` implements `IVariantFactory<FillCell, TCoord, FillMove, FillState<TCoord>>`. It keeps `GameId.of('hexa-fill')` in a private field and answers `isFor(gameId)`, so the composition root finds it by the id of the game (#234). It keeps the [`GeometryFactory<TCoord>`](../src/domain/engine/geometry-factory.ts) that it receives in its `geometry` attribute, and it builds its board with a [`BoardBuilder`](../src/domain/engine/board-builder.ts) over that geometry (D11). The composition root chooses the family, for example [`HexGeometry`](../src/domain/engine/hex-geometry.ts), so the same factory runs on any figure. It creates the rules, the piece source, the scoring policy, the board, the progress model, the initial state and the history (decision 31). The factory creates no id of a match, a state or a board. `createTimer(matchId)` takes the `MatchId` of the game: Hexa Fill has no timer and returns `undefined`, and a timed variant builds the `LevelTimerId` of its timer from it (decision 50). `GameFactory` wraps the rules of a timed variant in `TimedRulesDecorator` and gives the timer to the root. `createBoard(boardId)` passes the [`BoardId`](../src/domain/engine/board-id.ts) that it receives to `BoardBuilder.build(boardId)`. `createInitialState(matchId, stateId, boardId)` gives the first state its `GameStateId`, the `MatchId` of its game and the board of `createBoard(boardId)`. `GameFactory` asks its `MatchIdGenerator` for the `MatchId`, builds the two local ids from it and gives the same `MatchId` to the `GameEngine`. For the parts that it does not write, it picks engine classes: `SeededPieceSource` or `FixedListPieceSource`, `HighScoreProgress` or `LevelProgress`, `MoveHistory` or `RedoableHistory` (decision 3). `createProgressModel()` gives `LevelProgress` the level of the game, which implements `ILevelStars` (decision 36). A part that the game does not have, such as a piece source or undo, is none.
6. If Hexa Fill has levels, write `FillLevel` and `FillLevelBuilder`, which implements [`ILevelBuilder<FillLevel>`](../src/domain/progress/level-builder.ts) and builds the level step by step (D9). Its `withTopology()` refuses a topology of another family, and its `withSection()` checks the section of the Fill level file and turns each coordinate into a `TCoord` with the `GeometryFactory` that the builder holds. Add one level file per level in `src/adapters/levels/fill/`, in the shared level format (DS-6). Import each file in [`BundledLevelRepository`](../src/adapters/bundled-level-repository.ts), which reads it into a [`LevelDefinition`](../src/domain/progress/level-definition.ts) (#168). The definition directs the builder: the topology, then the section (decision 24). [`FitLevelBuilder`](../src/domain/variants/hexa-fit/fit-level-builder.ts) is the example.
7. If Hexa Fill publishes its own events, write classes that extend `GameEvent`, for example `RegionFilled`.
8. In layer 3, write `FillStateMapper`, which implements [`StateMapper<FillCell, FillView, FillCellView, FillPayloadView>`](../src/adapters/state-mapper.ts). `toView(cell)` turns each cell into a `FillCellView`, `freeView()` gives the view of a free space, and `toPayload(payload)` turns the `view()` of the photo into a `FillPayloadView` (#170). Write `FillMoveMapper` too, which implements [`MoveMapper<FillIntent, FillMove>`](../src/adapters/move-mapper.ts) in `src/adapters/` (#405). `FillIntent` is the plain data that the move controls send, such as a text id, a number or a pressed space. `toMove(intent)` turns that data into the value objects of the variant and builds the `FillMove`. [`FitMoveMapper`](../src/adapters/fit-move-mapper.ts) is the example.
9. In layer 4, write `FillCellRenderer`, which implements [`CellRenderer<FillCellView>`](../src/infrastructure/board/cell-renderer.ts). Its folder is `src/infrastructure/board/` (S3-07 in #151, «Propuesta, pendiente del equipo»), and Q8 can still move it. Write `FillControls` too, which implements [`MoveControls<TCoord, FillCellView, FillPayloadView, FillIntent>`](../src/infrastructure/ui/move-controls.ts) in `src/infrastructure/ui/` (#175): its `render(props)` draws the board with `board(onPressSpace)`, builds a `FillIntent` from each press and sends it with `play(intent)`. The controls import no class of `src/domain/variants/` (rule `ui-no-variants`): the move mapper of step 8 builds the move (#405). [`FitControls`](../src/infrastructure/ui/fit-controls.tsx) is the example.
10. Register the game: add `registered(GameId.of('hexa-fill'), new FillFactory(geometry, …), { mapper: new FillStateMapper(), renderer: new FillCellRenderer(), controls: new FillControls(), moves: new FillMoveMapper(), layoutOf: (size) => figure.layoutOf(size) }, worldTone(4))` to the list of `registeredGames(figure, clock, random)` in [`src/infrastructure/registered-games.ts`](../src/infrastructure/registered-games.ts). `geometry` and `layoutOf` come from the board figure that the player chooses, so the game runs on the hexagon, the square and the triangle (#171). The tone argument is the color of the game on the map: it is required, so the new game cannot type-check without one, and it stays the same on every figure (#298). `registered()` is the one place that pairs the id with its factory: it asks `FillFactory.isFor()`, and a factory of another game throws a `RangeError` (#234). [`GameRegistry`](../src/infrastructure/game-registry.ts) then maps `hexa-fill` to `FillFactory`, and the game selector map shows the new entry, because `HomePresenter` reads the ids of the registry (#169). The entry also holds the screen parts of the game (#170): `registered()` checks that `FillStateMapper` reads the cell and the payload of `FillFactory`, that the layout places its coordinate, that `FillCellRenderer` draws the cell view of the mapper, that `FillControls` read the views of the mapper and send a `FillIntent`, and that `FillMoveMapper` turns that intent into a `FillMove` (#405). The registry has no default parts: a new variant writes its own state mapper, move mapper, cell renderer and move controls (steps 8 and 9), as each of the four games does since #174 to #177 with `linesScreen()`, `fitScreen()`, `sortScreen()` and `mergeScreen()`. Its cell renderer can draw a free space with [`SpaceCellRenderer`](../src/infrastructure/board/space-cell-renderer.tsx), as the four cell renderers do. The game screen then shows Hexa Fill with no change of `GamePresenter`, `GameStage` or the route. [`CompositionRoot`](../src/infrastructure/composition-root.ts) gives the id and the `FillFactory` of the entry to `LevelGameFactories`, which builds a `GameFactory` with the one `MatchIdGenerator` that every variant shares, and `StartGame` takes that `GameFactories` port (#172). A variant with level files also gives `registered()` its `LevelVariant`, which builds its level builder and its variant factory for each level: write it as `fillLevelVariant()` in [`src/adapters/level-game-factories.ts`](../src/adapters/level-game-factories.ts), next to `fitLevelVariant()` and `sortLevelVariant()`. The one `GameEventBus` of the root goes to every `ApplyMove`, which delivers the events that the engine records (#233, #362), so a new variant changes no wiring of events. When an event of Hexa Fill counts for an achievement, add one branch for its class to `onEvent()` of [`AchievementCounterListener`](../src/adapters/achievement-counter-listener.ts).
11. Test the rules of Hexa Fill in their own test suite. The engine tests and the tests of the other variants do not change.

The role of each new class decides its layer ([the rule of layers 3 and 4](architecture/layers.md#the-rule-of-layers-3-and-4)). A conversion that the team writes and that imports no package, such as `FillStateMapper`, goes in layer 3. A React component, such as `FillCellRenderer`, goes in layer 4.

## The three jury variations

In the defense the jury proposes «un nuevo tamaño de tablero, una política de puntuación distinta o una nueva forma de pieza» (§3.1). Each variation below names its real file. No variation edits a file of `src/domain/engine/`, of `src/application/` or of another variant (APP-NFR-06). A comment of an engine file is part of the engine too. View 2 of the [extensibility diagram](architecture/extensibility.md) draws the same places.

### A new board size

1. For Hexa Lines or Hexa Merge, change the constant of the game in [`src/infrastructure/registered-games.ts`](../src/infrastructure/registered-games.ts): `LINES_BOARD` or `MERGE_BOARD`. Each game has its own constant, so the change resizes one game only. The factory passes the size to `BoardBuilder.withRegion(size)`, and no factory file changes. For Hexa Merge, `mergeOn()` gives the one value to `MergeSettings.of()` and to the slide controls of the Merge screen, so the ways on the screen follow the lines of the new board (#369).
2. For Hexa Sort, change `radius` in the level file of the level, in `src/adapters/levels/sort/`. `SortLevelBuilder` turns it into the `RegionSize` of the board. `SORT_BOARD` in `registered-games.ts` is the size of the seeded Sort level of the first content.
3. Edit the expected numbers of the outer-layer tests that pin a board size: `should_build_each_board_on_the_geometry_of_the_figure_when_the_figure_is_chosen` in `test/infrastructure/composition-root.test.ts`, which counts the cells of each board on each figure, and `FOUR_BOARDS` in `test/app/game-screen.test.tsx`, which counts the spaces of the first board of each game. A region of size n holds 3n(n − 1) + 1 hexagons, n² squares or 2n² triangles.
4. Change the board row of the comparison table in `docs/REQUIREMENTS.md` §1, for example «Hexagon, radius 2 (19 cells)» (rule R-requirements in `AGENTS.md`).

### A new scoring policy

1. In the folder of the variant, `src/domain/variants/hexa-<name>/`, write a class that implements `IScoringPolicy<TState>`, or a bonus that extends the engine `ScoringDecorator`.
2. Return it from `createScoring()` of the factory of the variant, for example `merge-factory.ts`. This line is a change of the same variant, not of the engine.
3. Test the policy in its own suite in `test/domain/variants/hexa-<name>/`, and test the factory line in the factory suite.
4. When the class bounds a type parameter, add a row to the README table «Variant bounds». `test/docs/generic-bounds.test.ts` fails on a bound in a variant folder with no row (APP-NFR-05).
5. When the policy changes the points of the game, change the README section «Scoring» (APP-FR-06). `test/docs/scoring-docs.test.ts` checks it. Add the class to the `IScoringPolicy` row of the extension-points table of the [extensibility diagram](architecture/extensibility.md).

### A new piece shape

A shape is data of one figure. It cannot be written once for every figure: the same pair of numbers names another cell on the triangle than on the hexagon.

1. For Hexa Fit, add the piece to `pieces` in the level file, in `src/adapters/levels/fit/`, or to `firstFitLevel()` in `registered-games.ts` for the level of the first content. `FitLevelBuilder` checks it.
2. For Hexa Lines, add the shape as data of its board figure in [`src/infrastructure/registered-games.ts`](../src/infrastructure/registered-games.ts), and give `LinesSettings.of()` the shapes of the geometry followed by the shapes of the figure. The first shape of a figure also adds the optional list `linesShapes` to `BoardFigure` and fills it in `boardFigures()`, as the rehearsal branch `odjaramillo/app-53-rehearsal-piece-shape` does. The lists in `HexGeometry`, `SquareGeometry` and `TriangleGeometry` are the base set of each geometry family, and they do not change.
3. Test that the Lines pieces of that figure include the new shape, in a test of `test/infrastructure/` that draws the pieces of the registry entry.

## Check

Before the defense, a branch adds Hexa Fill with these steps. Its diff must touch no file under `src/domain/engine/`, `src/application/` or the four other variant folders (APP-NFR-06). The same check applies to the [three jury variations](#the-three-jury-variations): a new board size, a new scoring policy and a new piece shape.

### Rehearsal of 2026-11-25

The rehearsal showed these facts, and [#369](https://github.com/Hexablock-Suite/hexablock-app/issues/369) fixed the documents and the code:

- The place of a board size and of a Lines piece shape is `src/infrastructure/registered-games.ts`. The section «The three jury variations» and view 2 of the [extensibility diagram](architecture/extensibility.md) now name that file.
- The comments of the three geometry files of the engine said «A new shape is one new line», and sent a developer to an engine file. They now name the file of a new Lines shape.
- Sort and Merge shared one board constant, and the slide controls of Merge read it apart from `MergeSettings`. Each game now has its own constant, and `mergeOn()` gives the Merge value to both.
- A size change edits the expected numbers of two outer-layer tests, and a new generic bound in a variant folder needs a row in the README table «Variant bounds». The steps above name both.

To repeat the rehearsal before the defense, cherry-pick the commit of each branch on the `main` of that day. Then run `pnpm verify` and the `git diff --name-only` check above.
