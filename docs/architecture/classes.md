## Whole model in draw.io

[`classes.drawio`](classes.drawio) holds the whole class model in one draw.io file, with 5 pages. Open it in draw.io or diagrams.net.

- Page 1, `All classes`, holds every class, interface and type of the model once, by layer: layer 4 at the top and layer 1 at the bottom, so every dependency points down.
- Pages 2 to 5, `Engine`, `Variants`, `Use cases` and `Adapters`, hold one part each. A part page shows the types of its part in full. A grey box with the name only is a type of another part that one of its lines touches, and its eyebrow names the page that details it.
- A solid box is a type that existed in the code at the commit of the last generation. The title of each page names that commit. A dashed box with `«planned»` is design from the views of this page that the code does not have yet. It keeps the `«Sprint N»` of its view when the view gives one.
- `members not designed yet` marks a planned class that no view details.
- `«dataType»` marks a type in the code that only carries data; it has no operations by design.
- The pages follow the reading rules of the next section, and each page has a legend.

The file is generated from the code at that commit plus the views of this page. A hand edit is lost at the next generation. The planned decisions 41 to 49 are not in it, because no view draws them yet.

## How to read it

- The colored zone is the Clean layer, with the colors of [layers.md](layers.md). Parts 1 and 2 are layer 1, entities, so their zones are yellow.
- In parts 3 and 4, one view can show several layers. The zones are bands, with the outer layer at the top and the inner layer at the bottom, so every dependency points down.
- A dashed frame groups the classes of one GoF pattern or one design principle. Its label names the source, for example `STRATEGY · §3.3 · D1`.
- A stereotype such as `«Strategy»` marks the role of one class in that pattern. Zone, frame and stereotype never carry the same information.
- The dashed box at the top right of a class holds its type parameters. This is the UML template notation that §4.1 asks for. A class declares there every parameter that its members name, for example `TCoord`. A bound on a parameter goes in the same box, for example `TState extends BoardState‹TCell, TCoord› & Cloneable‹TState›` on `GameEngine`. No line draws a bound, because a bound is not a parameter, a return value or a local variable.
- Every operation shows the type of each parameter and its return type. One operation has the same signature in every view. Every use case box shows `execute()` with the request and response types of its `UseCase` binding. In the class of 2026-11-02 the professor said that a class with no operations, or with operations that leave out their parameters, is wrong.
- The teal class is the focal class of the view.
- An italic class name or operation is abstract.
- A solid line with an open arrowhead is a use: the other class is an attribute, a parameter, a return value, a local variable or a `new`. Every dependency between two layers is a use. When the class keeps the other class in an attribute, the arrow end names the attribute and its multiplicity, even when it is 1, for example `games 1`. Otherwise the line carries a verb, for example `PLAY()` or `«create»`.
- Inside one layer, a diamond at the end of the holder marks an attribute only where it makes a GoF pattern visible: Strategy, Decorator, Composite, Observer, Command, State, Adapter, or a builder or a factory that holds its geometry factory. It is hollow (aggregation) when the value comes from outside, and filled (composition) when the class creates it. The other end names the attribute and its multiplicity. Any other attribute is a use with the attribute name and its multiplicity, also between an aggregate and its parts or an entity and its value objects, because the class box already shows the attribute. In the class of 2026-11-02 the professor kept the diamond for a pattern: «Aquí sí porque quiero hacer visible el patrón estratégico» (decision 23).
- No line starts or ends on a dashed frame. A map draws a line between two groups from the chip of the class that holds, calls or implements to the chip of the class it needs, with the same rule as a view: an attribute shows its name and multiplicity, for example `phase 1`, and any other use shows a verb, for example `CREATES`. A line from frame to frame would claim that every class of one group uses every class of the other. In the session of 2026-11-03 the professor asked about such a line: «todas esas usan los tres bloques de abajo, a lo mejor la respuesta es no». A map draws only the main dependencies, one or a few for each pair of groups. The view of each group shows the rest.
- The legend of each view lists only the line kinds that the view draws.
- In the variant views, a lollipop (a circle on a short line) is an engine interface that the class implements. Its label names the type that each parameter takes, for example `IGameRules‹PlacePiece, LinesState›`.
- In a map, a chip is one class with its name only. Every line of a map starts and ends on a chip. The group header names the view that shows the members, for example `VIEW 2`.
- In the variants map, a dashed chip is an engine type. Each class in its row implements or extends it.
- A dashed box with no members is a class that another view details. Its eyebrow names that view, for example `PART 1 · VIEW 1`.
- Under the name of a use case, an ID such as `APP-FR-08` names the requirement it serves.
- `UseCase` and `UseCaseAspect` name architecture roles, not game concepts. `UseCase` is the generic input port, the «input boundary» of Clean Architecture, and every use case implements it (decision 9). `UseCaseAspect` is the abstract base of the AOP decorators of view 3.1. APP-NFR-11 asks one aspect to cover the four variants, so all use cases need one shared contract, and its name states that role. The professor's rule «Tiene que tener semántica del problema» (class of 2026-10-16) applies to the entities, the concrete use cases and the ports, and they follow it: for example `ApplyMove`, `MoveHistory` and `RunningGameStore`.
- `«port»` marks an interface of layer 2 that an outer layer implements. Ports live in the application layer (decision 25). The engine and layer 3 have other interfaces that an outer layer implements, such as `Clock` and `KeyValueStore`. They carry `«interface»` only. `«aggregate root»` marks the entity that guards a game (decision 26). `«value object»`, `«entity»`, `«aggregate root»`, `«domain event»`, `«factory»` and `«repository»` are the tactical stereotypes of the domain design. A factory box carries `«factory»` next to the role of its design pattern, for example `«Concrete Factory» «factory»`, and a repository port or adapter carries `«repository»` next to `«port»` or `«Adapter»`. A box with no tactical stereotype is a piece of a design pattern: its pattern stereotype or its frame names its role. `RunningGameStore` carries no `«repository»` (decision 10). A question in the stereotype line, such as `«composition root» · Q9`, marks a placement that the professor's answer can move.
- The code holds the engine in `src/domain/engine/`, the four variants in `src/domain/variants/` and, of layer 2, `StartGame`, `ApplyMove`, `UndoMove`, `LoggingAspect` and their ports in `src/application/`. A class with a `«Sprint N»` stereotype is planned. View 2 draws two members that the code adds: `GridTopology.key(c: TCoord): CoordKey`, because the board stores its cells by a key, and a `contains: (c: TCoord) => boolean` parameter on `GridTopology.line()`, so the topology stops the line at the edge of the board. `Board.contains(c: TCoord): boolean` exposes the same test. `Board.line()` through a coordinate outside the shape yields nothing. The `Board` constructor throws a `RangeError` for an initial entry outside the shape and for an entry whose key differs from `GridTopology.key()` of its coordinate. It copies each entry, so the caller and the board share no tuple. `Piece.translated(offset: TCoord, topology: GridTopology<TCoord, string, string>): Piece<TCell, TCoord>` moves the shape through `ShapeNode.translated()`, so the triangle test of decision 16 can translate a piece. Issue #86 closes the primitive types of view 2 (APP-NFR-25): `GridTopology<TCoord, TAxis extends string, TDirection extends string>` and `Board<TCell, TCoord, TAxis extends string>` carry the closed axis and direction unions of each topology, `ring()` takes a `Radius` (a whole number of zero or more), `region()` a `RegionSize` (a whole number of one or more), `rotate()` and `rotated()` a `Turns` (any whole number). Each `of()` accepts only a safe integer (`Number.isSafeInteger`) and stores `-0` as `0`, and `key()` returns `CoordKey`, a branded string. `Board.topology` and the shape operations take `string` for the unions they do not read, and `BoardSnapshot.board` is a `ReadonlyBoard<TCell, TCoord, string>`, so `GameEngine`, `IGameRules` and `BoardState` gain no type parameter. The README table «Primitive types» gives the reason for each primitive that stays. `GamePhase.resume(): GamePhase` ends a pause. A phase keeps its name private: `GamePhase.checkAcceptsMove(): void` and `checkAcceptsUndo(): void` throw the `RangeError` that names the phase when the phase refuses a move or an undo, so `GameEngine` does not read the name. `Resolution` is a value object that holds an `accepted` flag and the `Outcome`, and no state: `equals()` compares both values (decision 26), and `Outcome` is the closed union `playing`, `victory` or `game-over`. `GameEngine` takes its `MatchId`, its `GameId` and its `GameEventPublisher` in the constructor, answers its phase through `currentPhase()`, has `resume()`, and takes an optional `MoveHistory` for undo (APP-FR-08, decision 3). `SeededPieceSource` takes a `seed` and builds its own `Mulberry32Random`, an engine `RandomSource` with the Mulberry32 generator, so the same seed gives the same pieces. Each source and `Mulberry32Random` has `clone()`, which copies the position or the generator state (decision 31). The seed is an integer from 0 to 4294967295, and any other number throws a `RangeError`, so no seed is truncated into another. `FixedListPieceSource` throws a `RangeError` on a list that holds `undefined`, and it reads its list once. `IRandomSeeded` holds the `seed`. `BaseGameRules` adds the protected step `noValidMove(state: TState): boolean`, the end check of decision 33, so each variant `evaluate()` reuses it. `ProgressRecord` is a draft with `gameId`, `score`, `levelId` and `stars`: view 4 shows these fields, and the real progress models of Sprint 3 can add fields. `GameResult.of()` throws a `RangeError` for a decimal or negative move count and for a time that is not finite or is negative. `ProgressRecord.of()` throws one for stars that are not finite or are negative. The score of both is a `Score`, which checks its own value (decision 41). Stars can be decimal, because no requirement says that they are whole numbers (decision 36).

21. **Template Method in an abstract base class.** The abstract `BaseGameRules` implements `IGameRules`. When `resolve()` rejects the move, `playTurn()` returns that rejected resolution and does not call `evaluate()`. A rejected move never ends the game, and two guards enforce it. `Resolution.evaluated()` on a rejected resolution throws a `RangeError`, so a custom `playTurn()` that evaluates a rejected resolution fails, and `GameEngine.play()` rethrows that error with the state kept. The engine computes the next phase before it commits the turn. An outcome that the phases do not know throws a `RangeError`, and the state and the phase stay as they were. When a turn throws, the rollback covers the whole state and the phase. The piece source lives in the state (decision 31), and the state `clone()` clones it. So a turn that is retried after a throw draws the same piece, and a move that `resolve()` rejects leaves the source at its old position. A `Resolution` holds no state, only `accepted` and the `Outcome`: the rules change the state that they receive in place, so the engine reads the copy that it gave them. `GameEngine` depends only on the interface `IGameRules`, so the Strategy of D1 stays, and a decorator such as `TimedRulesDecorator` can wrap any rules. 28. **Use cases return a `Result`.** In Clean Architecture an exception must not reach the screen. `UseCase.execute(request: TRequest)` returns `Promise<Result<TResponse>>`. `Result<T, E = UseCaseError>` holds a value or an error, and `Result.success(value: T)` and `Result.failure(error: E)` create it. `UseCaseError` has a `code`, a `message`, a `retryable` flag and an optional `cause`. An empty or blank `code` throws `RangeError("A use case error needs a code.")`, because the presenter picks its message by the code (G117.6). `caughtError(code, thrown)` builds the error of a caught exception and keeps the thrown value as its `cause`, so the log still shows a programming error. It never throws: a thrown value whose text `String()` cannot build, such as `Object.create(null)`, gets the fixed message «The thrown value has no text.» and stays the `cause` (issue #138). `RetryAspect` runs the use case again while the error is retryable, and the presenter shows the message through `GameViewModel.error`. An aspect puts its concern in the protected `around()` and calls `super.around()` to run the inner use case, which gives an `unexpected-failure` `Result` when the inner promise rejects. A failed `Result` of the inner use case passes through unchanged. The failure codes: `start-failed`, `no-running-game`, `move-rejected`, `move-failed`, `publish-failed` (only in the log, see decision 29) and `unexpected-failure`. Views 3.1, 3.5 and 4.1.

View 1 of [extensibility.md](extensibility.md). **The pair of terms.** `GameId` says which game it is, for example `hexa-lines`: two matches of Hexa Lines have the same `GameId`. `MatchId` says which match of that game: the «partida» of the statement, one game that a player starts and plays to its end. `MatchId` in `src/domain/engine/match-id.ts` is a value object over a private text. `MatchId.of(value: string): MatchId` rejects an empty or blank value with `RangeError("A match id cannot be empty.")`, and `equals()` compares two ids. `GameEngine` holds both ids, and `GameOver` carries both, as `gameId` and `matchId`, so a listener tells two matches of one game apart. The older names with «game», such as `GameOver` and `StartGame`, still speak of one match. View 5.
31. **The variant factory creates the whole family.** Statement §3.3 asks one factory per variant for the rules, the piece source, the scoring policy and the board. `IVariantFactory` has `createPieceSource(): IPieceSource<Piece<TCell, TCoord>> [0..1]` and `createBoard(boardId: BoardId): Board<TCell, TCoord, string>` next to `createRules()` and `createScoring()`. `createInitialState(matchId, stateId, boardId)` puts the board and the piece source in the first state, gives the state its own `GameStateId` and the `MatchId` of its game (decision 26), and gives the board its `BoardId` (decision 7). The state draws from its own source when the rules call its methods. A variant with no piece source returns none, and its state holds no source. `BoardState` has no source field: the state type of a variant adds it. `IPieceSource` and `RandomSource` are `Cloneable` (Prototype, decision 7). `SeededPieceSource.clone()` and `FixedListPieceSource.clone()` copy their position, and `Mulberry32Random.clone()` copies its generator state. No clone replays the draws. The state `clone()` clones its source, so the copy and the rollback of `GameEngine.play()` cover the source, and the engine has no code for it (decision 21). View 5 and view 1 of [extensibility.md](extensibility.md).
32. **`IPieceSource` is Strategy and Iterator.** `IPieceSource<TPiece>` keeps `hasNext(): boolean` and `next(): TPiece`, and adds `[Symbol.iterator](): Iterator<TPiece>`. So a rules class or a test reads the pieces with `for...of`, and the language protocol replaces a custom loop. The Strategy stays: the variant factory picks the source. `SeededPieceSource` never ends, because `hasNext()` is always true. `FixedListPieceSource` ends after its last piece, so the Fit tray is finite. A caller that reads a seeded source with `for...of` stops the loop itself. Team decision D16. View 4.
33. **`IGameRules.validMoves()`.** Statement §3.1 says that the rules «define los movimientos válidos». `isValid(state, move)` checks one move, and `validMoves(state: TState): Iterable<TMove>` gives the valid moves. Each variant writes it as a lazy generator: it walks the board with `Board.line()`, `ring()` and `neighborhood()` and yields one valid move at a time. The end condition «no valid move» of Lines, Sort and Merge asks for the first move and stops there, so it never builds the full list. A hint or a test can read more moves from the same generator. `BaseGameRules` leaves the method abstract, and `TimedRulesDecorator` passes it to its inner rules. `IGameRules` keeps two type parameters, `TMove` and `TState`, because the method names no cell and no coordinate. Team decision D17. Views 1 and 7.
34. **Memento in the undo history.** `MoveCommand.before` is a Memento. `GameEngine` is the originator: for each turn it takes the photo of the state before the move with `BoardState.snapshot()` and keeps it in a new `MoveCommand`. The photo, a `BoardSnapshot` of the variant (`SnapshotOf<TState>`), is the memento, and the same kind of photo gives the screen data and the answer of `GameEngine.snapshot()` (unit R8). It is immutable, so the command keeps it with no copy. It holds the position of the piece source, so an undo draws the same piece again. `MoveHistory<TMove, TMemento>` is the caretaker: it keeps the commands and never reads the photo inside them. `undo()` gives the kept photo back to the engine, and the state takes it back in place with `BoardState.restore()`. The engine is the Command receiver: when it records a turn, it gives the new `MoveCommand` its private `restore(memento)` as a function. `MoveCommand.undo()` calls that function, so `undo()` returns `void` and no public member of the engine replaces its state (#159). A paused game refuses the undo. A finished game and a new game forget their moves. Memento is not one of the fourteen patterns of §3.3, so it adds no row to the patterns table. The Command row names it. Team decision D18. View 3.
35. **No Visitor and no Mediator.** D3 allows a Visitor only inside the shape Composite, where the node types are closed and the operations grow. Today `ShapeNode` declares each operation (`cells()`, `area()`, `rotated()` and `translated()`), and no class implements a Visitor. A Visitor over the variants would make every new variant edit every visitor, and that breaks the extensibility test (APP-NFR-06). So the design discards Visitor, and the reasoning of D3 stays as its record. `GameEventBus` is an Observer: it implements `GameEventPublisher` and sends each event to its listeners. It does not coordinate classes that call each other, so the design does not claim Mediator. Team decision D19. Views 2 and 4.3.
36. **Composite only for shapes, and stars are data.** Composite stays in `ShapeNode`, `CellNode` and `ShapeGroup`, because a piece and a Fit figure are trees of cells (piece shape row of §8). An `EndCondition` composite and a `StarRule` composite were proposed and discarded: no source declares a variation in end conditions or star rules, and D5 asks for a written reason for each abstraction. Fit stars are data. Each level file holds two thresholds per star: a move count and a time. `FitLevelBuilder` reads them from `LevelDefinition` and puts them in the `FitLevel` (decision 24). `LevelProgress` compares the moves and the elapsed time of the `GameResult` with them. The stars are cumulative: star N needs star N-1, so `fitStars()` counts the leading thresholds that the play meets, as `sortStars()` does (gap G110.5). A play holds a `Moves` and an `ElapsedTime`, and each threshold is a value object that tells whether a play meets it (decision 42). So `fitStars()` and `sortStars()` check nothing: `Moves.of()` throws a `RangeError` for a move count that is not a safe integer of 0 or more, and `ElapsedTime.ofMs()` throws one for a time that is not a safe integer of 0 or more (gaps G110.1 and G110.2, issue #137). Both functions return `Stars`. `FitState.moves` counts the moves of the game: `FitRules.apply()` adds one for every accepted place, rotate and remove, and a rejected move counts nothing (issue #60). The count lives in the state, so `clone()` keeps it. The clone in `MoveCommand.before` therefore holds the count before the move, and undo gives it back (decision 34). Team decision D20. View 2 and the Fit view.
37. **The `Logger` port takes a log entry, not a message.** `Logger.log(entry: UseCaseLogEntry): void` receives the name of the use case, the outcome (`"success"` or `"failure"`), the elapsed time when `TimingAspect` measures it, and the `UseCaseError` of a failed `Result`. `LoggingAspect` and `TimingAspect` build the entry, and `LoggingAspect(inner, logger, name)` rejects an empty or blank `name` with `RangeError("A logging aspect needs a name.")` (G118.4). `ApplyMove` builds one more entry: the `publish-failed` failure of decision 29, whose call still answers success. It formats no message either. `ConsoleLogger`, the adapter in layer 4, writes the text. In the class of 2026-11-02 the professor said that a message parameter makes the caller build the message, and that the message belongs in the implementation of the port, a secondary adapter. So no use case and no aspect formats a message. View 3.1 and the map of Part 3.
38. **`Range<T>` for two-sided limits, and `GoalCount` for the Sort goal.** `Range<T>` in `src/domain/engine/range.ts` is a closed interval `[min, max]` over any ordered type, with `contains(value: T): boolean`. `Range.of(min, max, compare)` takes a `Compare<T>` function, and `Range.ofNumbers(min, max)` compares numbers. Both throw `RangeError("A Range needs min <= max.")` when min comes after max. It mirrors the `Range<T>` of hexablock-api. The seed of `Mulberry32Random` (0 to 4294967295) and the chance of a 4 of `mergeTileSource()` (0 to 1) check their limits with it, and keep their messages. `GoalCount.of(n)` in `src/domain/variants/hexa-sort/goal-count.ts` holds the goal of a Sort level: a safe integer of 1 or more, with no upper bound (decision on issue #129). A goal of 0 won before the first move, so `SortLevel.goalsNeeded` and `SortState.goalsNeeded` are a `GoalCount`, not a bare number (gaps G108.1 and G116.5). `GoalCount.isReachedBy(goalsDone)` tells if a count of cleared stacks reaches the goal, so `SortRules.evaluate()` does not read the number of the goal. The count of cleared stacks is a `ClearedStacks` (decision 42). `RegionSize`, `Radius` and `Turns` keep their own checks, because each one is already a value object with one bound. `Turns.normalized(topology)` reduces a count to one full turn of a topology, so the three topologies and `Placement` do not repeat that calculation. `Turns` keeps its number private. `plus(other: Turns): Turns` adds two counts. `applyTo(start, step, topology)` runs `step`, one rotation step of the topology, once for each step of the normalized count. `shorter(): Iterable<Turns>` gives each count from 0 up to the count, without the count. `GridTopology.fullTurn(): Turns` gives the full turn of a topology, 6 steps for a hexagon and 4 for a square, so no topology shows a number of rotation steps and `FitRules.validMoves()` reads `fullTurn().shorter()`.
39. **The space of the board is an entity, and `TCell` stays a value.** The class of 2026-11-09 models the place on the board as an entity, because it «puede pasar de libre a ocupada». `BoardSpace<TCell, TCoord>` in `src/domain/engine/board.ts` is that place. The topology key of its coordinate is its identity, and `equals()` compares that key. Its state is the `TCell` that occupies it, or none when it is free. Only `occupy()` and `vacate()` change that state, and `vacate()` throws a `RangeError` for a free space. `Board` gives no caller a space: `get()`, `occupy()` and `vacate()` speak in cells and coordinates, and `clone()` copies each space and shares the cell objects (decision 7). A space exists from its first write, so `cells()` keeps the first-write order. A vacated space is free, and a cell that occupies it again moves it to the end of that order. The two forms of a free cell stay: a coordinate with no space, and `ColorStack.empty()` in Sort. `occupation()` tells `Board` the coordinate and the cell of a space. The method is public because TypeScript has no module visibility and the tests read the state through it. No other code in `src/` calls it. How a domain object shows its state is still a question for the professor.
40. **`GameFactory` creates the whole aggregate.** `GameFactory<TCell, TCoord, TMove, TState>` in `src/domain/engine/game-factory.ts` is the DDD factory of the aggregate: it creates the root with all its parts as one piece. It takes an `IVariantFactory`, a `MatchIdGenerator`, a `GameStateIdGenerator`, a `BoardIdGenerator` and a `GameEventPublisher`. One generator gives each kind of id, as `MatchIdGenerator` does, so each concept keeps one name. **The generators guarantee uniqueness** (decision of 2026-11-10 on #212): each `next()` of `MatchIdGenerator`, `GameStateIdGenerator` and `BoardIdGenerator` gives an id that the generator did not give before. `GameFactory` does not check it and keeps no list of the ids that it gave: such a list would live only as long as one `GameFactory`, and no code compares two games, two states or two boards of different matches. So a generator that repeats an id gives two games with equal engines, equal states and equal boards, and the test `should_hold_equal_states_and_boards_when_a_generator_repeats_an_id` in `test/domain/engine/entity-ids-regression.test.ts` pins that behaviour. Only test generators exist today. The real generators of layer 4 come with the composition root (#162) and must keep this contract, for example with a UUID. `createGame(): GameEngine<TCell, TCoord, TMove, TState>` asks each generator for one new id, asks the variant factory for the rules, the scoring, the history and the first state with its three ids, and returns the started `GameEngine`. `IVariantFactory` stays the Abstract Factory that creates the family of parts of one variant (decision 31), and it has no `createGame()`: to put the parts together is the same work for every variant, so one engine class does it once, and a fifth variant writes no assembly. `StartGame` keeps the `GameFactory` and the `RunningGameStore`: it asks for the started game and stores it, so no use case builds a domain object part by part. An error of the generator or of the variant factory leaves `createGame()` as it is thrown, and `StartGame` answers `start-failed`. The composition root gives the three generators and the publisher to the `GameFactory` (#162). Views 5 and 3.2, and flow 3.
41. **`Score` replaces the number of every score (#203).** The class of 2026-11-09 forbids primitives in the domain model, except the boolean, and gives the score as the example of a value object. `Score` in `src/domain/engine/score.ts` is a value object: `Score.of(value)` checks the value, `equals()` compares two scores by value, and the object is frozen. One rule holds for the score of a game and for the points of a turn: a safe integer of 0 or more, the rule of the backend `Score` (hexablock-api#87). Any other number throws a `RangeError`, and `-0` counts as 0. So the app never keeps a score that the backend refuses. Before #203 the app took any finite number. `add()` gives the sum of two scores as a new `Score`, and a sum above `Number.MAX_SAFE_INTEGER` throws a `RangeError`. `times(factor)` gives the product of a score and a whole factor of 0 or more, with the same limit, and any other factor throws a `RangeError`. `isHigherThan()` tells which of two scores is higher, and an equal score is not higher. `BoardSnapshot.score`, `BoardState.addPoints()`, `IScoringPolicy.score()`, `ScoringDecorator.score()`, the five scoring policies, `GameOver.finalScore`, `GameResult.score` and `ProgressRecord.score` take or return a `Score`, and each variant state keeps one in a private field. The checks of a finite score in `GameEngine`, `GameOver`, `GameResult`, `ProgressRecord` and the four states are gone: a `Score` is valid when it exists. The state still changes in place (decision 7): `addPoints()` replaces its `Score` with the sum. A policy that gives no valid score throws inside the turn, and so does a total above the largest safe integer. Both leave the turn unsaved, with the board, the score and the phase as they were. A use case never opens a domain object, so `MoveResult.score` carries the `Score`, and the presenter of layer 3 asks for the number. The counters of #204 and the outcome of #207 follow the same rule. `Score.value` stays readable, as in the backend `Score`, because the professor names the operation that gives the number to an adapter in the class of 2026-11-13. Until then no line of `src/domain/` or `src/application/` outside `Score` reads it, and the README table «Primitive types» keeps its row with that reason. `LinesScoring.lineBonus()` and `MergeTile.points()` return a `Score` too, so no class of `src/domain/` has a score of type `number` in a public signature. `MergeScoring` adds the points of the merged tiles with `add()`. `ComboMultiplierDecorator` multiplies the line bonus with `times()`, and it adds nothing when the placement clears no line, so no negative factor reaches `times()`. The factor of `times()` is a count, not a score, and the README table gives its reason. APP-NFR-25 now states the rule of the class. Views 1, 4 and 5 draw the `Score` box.
42. **Counters are value objects (#204).** `Moves`, `ElapsedTime`, `Stars` and `LevelId` in `src/domain/engine/` replace the numbers and the text of the move count, the time of play, the stars and the level id, with the names of the backend twin (hexablock-api#88). Each one is a value object: its factory checks the value, `equals()` compares two values, and the object is frozen. The rule is the rule of the backend, so the app never keeps a value that the backend refuses. `Moves.of()`, `ElapsedTime.ofMs()` and `Stars.of()` take a safe integer of 0 or more, throw a `RangeError` for any other number, and store `-0` as 0. `LevelId.of()` keeps the text as it arrives and throws a `RangeError` for an empty or blank id. Before #204 a time and a star count could have a fraction: `GameResult` took any finite time of 0 or more, and `ProgressRecord` took any finite star count of 0 or more. `Moves.plusOne()` gives the next count, `Moves.isFewerThan()` and `ElapsedTime.isShorterThan()` compare two values, with the names of the backend. `checkMoveCount()` and its file `move-count.ts` are gone: the check lives in `Moves.of()`. `GameResult` holds a `Moves`, an optional `LevelId` and an optional `ElapsedTime`, and `ProgressRecord` holds an optional `LevelId` and optional `Stars`. Neither has a check of its own, and `equals()` asks each value object. `ITimed.elapsedMs()` and `LevelTimer.elapsedMs()` return an `ElapsedTime`. `LevelTimer` still gives 0 for a clock that goes back, and it drops a fraction of a millisecond, because an `ElapsedTime` is a whole number. `LevelTimer` stays a plain class here: it becomes an entity in #214. `FitState` keeps a `Moves` in a private field, its photo carries it as `FitSnapshot.moves`, and `FitState.countMove()` still changes the state in place (decision 7): it replaces the `Moves` with `plusOne()`. `FitState.restore()` no longer checks the count of a photo, because a `Moves` is valid when it exists. The count of cleared Sort stacks is a counter too: `ClearedStacks` in `src/domain/variants/hexa-sort/cleared-stacks.ts`, with `plusOne()` and `isAtLeast()`. `SortState` keeps one, `SortSnapshot.goalsDone` and `SortView.goalsDone` carry it, and `GoalCount.isReachedBy()` takes it. `FitPlay`, `FitStarThreshold`, `SortPlay` and `SortStarThreshold` are value objects built on the counters, each with a factory method and `equals()`. A threshold keeps its limits private and `isMetBy(play)` tells whether a play meets it: a play that equals a limit meets it, and a play that passes a limit by one move or by one millisecond misses it. `fitStars()` and `sortStars()` count the leading thresholds that the play meets and return `Stars`, so the stars of a play are the same as before. A use case never opens a domain object, so `MoveResult.elapsedMs` carries the `ElapsedTime` (decision 41). The `value` of `Moves`, `ElapsedTime`, `Stars`, `LevelId` and `ClearedStacks` stays readable, as in the backend twins, because the screen and the sync request need the number or the text, and the professor names the operation that gives it to an adapter in the class of 2026-11-13. Until then no line of `src/domain/` or `src/application/` outside each class reads it, and the README table «Primitive types» keeps the rows of the four engine classes with that reason. The seed stays a number until decision 48. `SortSnapshot.clearedTiles` stays a list of numbers: it is a fact of the last turn for the scoring, not one of the counters of #204. Views 3 and 4, Fit and Sort, and the `MoveResult` and `GameResult` boxes of flows 1 to 4 and of view 3.5.
43. **Every move is a value object (#205).** `PlacePiece`, `Slide`, `PlaceFitPiece`, `RemoveFitPiece`, `RotateFitPiece` and `PlaceStack` each have `equals()` and only private fields. The constructors and `Slide.of()` keep their signatures. `PlaceStack` is a class in `src/domain/variants/hexa-sort/place-stack.ts`, with a private constructor and the factory method `PlaceStack.on(at)`: an object literal is no longer a move. A move checks what it can check alone: `PlacePiece` throws a `RangeError` for a tray index that is not a safe integer of 0 or more, so `LinesRules.isValid()` has no check of the index. Before #205 the rules refused such a move, and now the move does not exist. The rules and the state keep the checks that need the board or the topology, such as the axis of a `Slide`, and they read no field of a move: they ask the move, or they pass it to a business method of the state. `LinesState` asks a `PlacePiece` for its tray piece (`pieceIn()`), for the tray without it (`trayWithout()`) and for the cells that the piece covers (`cells()`), and the move builds the two errors of a refused placement (`missingPiece()`, `misfit()`), so the messages stay the same. `MergeState` asks a `Slide` whether it lies on an axis of the topology (`isAlong()`), for the line through a cell (`lineThrough()`) and for the order of a line (`fromLeadingEdge()`). The three Fit moves have no `kind` field: `FitMove` stays a closed union, and `FitRules` tells the moves apart by their class. A Fit move gives its piece (`piece()`), a `PlaceFitPiece` gives its `Placement` (`placement()`), and a `RotateFitPiece` turns a placement (`turn()`). `SortRules` asks a `PlaceStack` for its cell (`cell()`). `piece()` and `cell()` return a value object or a coordinate of the domain, never a primitive. A Fit move compares its rotation count as the player gave it, and `Placement` still normalizes the count. Until decision 44 lands, a move compares its coordinate through `GridTopology.key()`, as `Placement` does, so the `equals()` of `PlacePiece`, `PlaceFitPiece` and `PlaceStack` takes the topology. `SlideSense` stays a union of two texts until decision 45. The four variant views draw the six moves as «value object» boxes, and `FitMove` as a «type» box.
44. **Coordinates are value objects (planned, #206).** `HexCoord`, `SquareCoord` and `TriangleCoord` become classes with private numbers, `equals()` and the operations on their own values, such as the sum, the opposite and the distance of two hex coordinates. The topology keeps what belongs to the grid: the neighbors, the lines, the rings and the regions. This changes decision 16 in one point: a coordinate does the calculation on its own values. `hex()`, `square()` and `triangle()` keep their signatures, and `GeometryFactory.createCoord()` keeps its list of numbers, because a level file has no types. `Radius` and `RegionSize` keep their number private. Whether `TCoord` gets a bound, so that `Board` and `Piece` can call `equals()`, is decided in #206. View 6.
45. **Closed unions are classes (planned, #207).** `Outcome`, `TopologyId`, `SlideSense` and the axis and direction unions of the three topologies become classes with a closed set of instances, `equals()` and an operation of their own. No domain code compares a text to know an outcome, a topology, a sense, an axis or a direction. A level file and a JSON body keep the texts, and a factory or an adapter turns a text into the class and refuses an unknown text. The axis and direction classes come after decision 44, because they change the same files and decision 16. Views 1, 2, 6 and Merge.
46. **`FitLevel` is a class (planned, #208).** `FitLevel` becomes a value object that guards its own invariant: a factory method, `equals()`, private fields and a frozen list of pieces. A level with two pieces of one id cannot exist, so `FitState.start()` no longer checks it. `FitFactory` keeps the check that needs its geometry: the topology of the level. `FitLevelBuilder` (#166) creates the level through the factory method. The Fit view.
47. **`SortLevel` holds the data of its source (planned, #209).** A value object never holds an object that changes. `SortLevel` becomes a class that holds the size, the goal and the data of its piece source: the seed or the fixed list of stacks. `SortFactory.createPieceSource()` creates a new source from that data for each game and clones nothing. The Sort view already draws this design. `SortLevelBuilder` (#167) creates the level through its factory method. The Sort view.
48. **Settings are classes and the seed is a value object (planned, #210).** `LinesSettings`, `MergeSettings` and `NewTile` become classes with a factory method, `equals()` and private fields, in the form of decision 46. `Seed` holds a whole number from 0 to 4294967295 and checks it once. The settings, `SeededPieceSource`, `IRandomSeeded` and `Mulberry32Random` take a `Seed`. `TurnReport` is not a domain concept: it carries a publish failure, so it leaves `src/domain/`, and `ApplyMove` still answers success with the saved turn when the publisher throws (decision 29). It comes after decision 46. Views 4, Lines and Merge.
49. **The board and the piece close their fields (planned, #211).** `BoardShape.cells`, `Board.shape`, `Board.topology`, `Piece.shape`, `Piece.content` and `PieceId.value` become private, and `ReadonlyBoard` shows no field. Each reader asks an operation with a business name or passes the object on. `FitState` keeps its pieces and placements in a domain collection that finds an entry by `PieceId.equals()`, not in a `Map` keyed by a text. The board keeps its `BoardId` (decision 7). It comes last, after decisions 43, 44 and 48, because they rewrite most of its readers. Views 2 and Fit, and flows 1, 3 and 4.

## Render the images

The maps and the views come from the HTML files in [`classes/views/`](classes/views/). Each file holds one inline SVG drawn with the diagram-design skill. Open the file in a browser to see the drawing. The `.png` image next to it is that SVG rendered at scale 2 by a headless browser. After you edit a file, export the image again with `/diagram-design:export-diagram docs/architecture/classes/views/<view>.html --png-only`, then run `pnpm format`. The formatter changes the HTML layout only; the drawing stays the same. Commit each `.html` file together with its `.png` image. When a class is added or removed, update its map and its view in the same commit.
