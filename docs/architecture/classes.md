## Whole model in draw.io

[`classes.drawio`](classes.drawio) holds the whole class model in one draw.io file, with 6 pages. Open it in draw.io or diagrams.net.

- Page 1, `All classes`, holds every class, interface and type of the model once, by layer: layer 4 at the top and layer 1 at the bottom, so every dependency points down.
- Pages 2 to 6, `Engine`, `Variants`, `Use cases`, `Adapters` and `Infrastructure`, hold one part each. A part page shows the types of its part in full. A grey box with the name only is a type of another part that one of its lines touches, and its eyebrow names the page that details it.
- A solid box is a type that existed in the code at the commit of the last generation. The title of each page names that commit. A dashed box with `«planned»` is design from the views of this page that the code does not have yet. It keeps the `«Sprint N»` of its view when the view gives one.
- A function component is code too (#392, option A). The generator reads `app/` and `src/`: the default export of each route of `app/`, such as `GameScreen`, and each exported function component of a `.tsx` file of `src/`, such as `BoardView`, is a code type of kind `component`. [`classes.config.json`](classes.config.json) places `app/` in layer 4, part `Adapters`, next to `src/infrastructure/`. A component box carries `«component»`, its name and its props as attributes. The generator follows a use into a top-level function of the same file, such as `wonCountOf()` for `LevelsWon` → `LevelStatus`.
- A grey line marked `planned` between two solid boxes is a use or a realization that a view draws and that the generator does not see in the code. Each one has a reason. `GameScreen` reaches `BoardView`, `GamePresenter`, `GameViewModel` and `MoveControls` through `GameStage` and `useGameSession()`, and `AchievementsScreen` reaches `AchievementsPresenter` through `useAchievements()`: the generator follows no function or component of another file. `ApplyMove`, `StartGame` and `UndoMove` read the cells and the free spaces through `moveResultOf()` of `move-result.ts`, another file, and that function reads a `ReadonlyBoard` from `BoardSnapshot.boardCopy()`, not a `Board`. View `engine-1-turn` draws no `IScoringPolicy` → `BoardSnapshot`: `score()` takes `SnapshotOf‹TState›`, a conditional type with `infer` that names no `BoardSnapshot`, and `IScoringPolicy‹TState›` does not bound `TState`, so the generator sees no such use. The view draws the code line `IScoringPolicy` → `SnapshotOf` instead, and each photo of a state is still a `BoardSnapshot` (decision 34). `LinesRules`, `FitRules`, `SortRules` and `MergeRules` → `IGameRules` are indirect: each rules class extends `BaseGameRules`, which implements `IGameRules`. `CompositionRoot` → `ConsoleLogger` «create» is in the default value of a constructor parameter, which the generator does not read. `GamePresenter` → `GameEventListener` is design of view `ad-3-events` that the code does not have yet.
- `members not designed yet` marks a planned class that no view details.
- A box with no operation says why. `«dataType»` marks a class in the code with no operation: it only carries data. No class of the app needs it today, so no legend lists it. An interface with no operation carries `«interface»`, next to the stereotypes of its views, such as `«value object»`, and never `«dataType»` on top. A union of literals, such as `Language`, carries `«enumeration»` and one literal per line. A type alias, such as `FitMove` or `ApiClient`, carries no kind word: its box shows its name and the aliased type or its members. **The change of 2026-11-24:** until that day the generator put `«dataType»` on every type in the code with no operation, interfaces included, and printed `«union»` and `«type»` as stereotypes. The views `variant-2-fit`, `flow-2-save-progress` and `flow-5-login` drew `«type»` on `FitMove` and `ApiClient` until then.
- A line of structure (extends, implements, composition) is thick. A `use` line is thin and light, and it lives in the draw.io layer `use lines`. Hide that layer in Edit > Layers to read the structure alone.
- Inside a group of 12 boxes or more, a frame holds the boxes of one view of this page. The frame title is the file name of the view in [`classes/views/`](classes/views/), for example `view engine-1-turn` for `engine-1-turn.png`.
- The pages follow the reading rules of the next section, and each page has a legend.

The file is generated from the code at that commit plus the views of this page, by the tool [`drawio-clases`](https://github.com/Hexablock-Suite/.github/tree/main/tools/drawio-clases) of the organization repository. The README of the tool gives the commands. [`classes.config.json`](classes.config.json) maps the folders and the views to layers and parts. [`classes.layout.json`](classes.layout.json) fixes the order of the groups of each band and of the boxes of each group.

A hand edit of that order survives. Move the boxes in draw.io, run `pin.mjs` of the tool to write the order into `classes.layout.json`, and generate the file again. Commit `classes.drawio` and `classes.layout.json` together. Any other hand edit is lost at the next generation: a pixel position, a line route, a text or a style.

## How to read it

- The colored zone is the Clean layer, with the colors of [layers.md](layers.md). Parts 1 and 2 are layer 1, entities, so their zones are yellow.
- In parts 3 and 4, one view can show several layers. The zones are bands, with the outer layer at the top and the inner layer at the bottom, so every dependency points down.
- A dashed frame groups the classes of one GoF pattern or one design principle. Its label names the source, for example `STRATEGY · §3.3 · D1`. A dark dashed frame labelled `AGGREGATE` marks the boundary of an aggregate (decision 52).
- The title of a frame names its pattern, or a note of the view names it. No box carries a role label of a pattern, such as `«Strategy»` or `«Decorator»`: the interface of a pattern carries only `«interface»`, and a concrete piece of a pattern carries no role label (decision 23). Zone, frame and stereotype never carry the same information.
- The dashed box at the top right of a class holds its type parameters. This is the UML template notation that §4.1 asks for. A class declares there every parameter that its members name, for example `TCoord`. A bound on a parameter goes in the same box, for example `TState extends BoardState‹TCell, TCoord› & Cloneable‹TState›` on `GameEngine`. No line draws a bound, because a bound is not a parameter, a return value or a local variable.
- Every operation shows the type of each parameter and its return type. One operation has the same signature in every view. Every use case box shows `execute()` with the request and response types of its `UseCase` binding. In the class of 2026-11-02 the professor said that a class with no operations, or with operations that leave out their parameters, is wrong.
- The teal class is the focal class of the view.
- An italic class name or operation is abstract.
- An underlined operation is static, for example `Score.of()`.
- A solid line with an open arrowhead is a use: the other class is an attribute, a parameter, a return value, a local variable or a `new`. Every dependency between two layers is a use. When the class keeps the other class in an attribute, the arrow end names the attribute and its multiplicity, even when it is 1, for example `games 1`. Otherwise the line carries a verb, for example `PLAY()` or `«create»`.
- A filled diamond (composition) at the end of the aggregate root marks each internal entity of its aggregate. The other end names the attribute and its multiplicity. A hollow diamond (aggregation) at the end of a decorator joins it to the type that it wraps, with the label `decorate` and the multiplicity `1` at the other end. An aspect is a decorator. The diamond sits on the class that declares the wrapped attribute. A decorator that inherits that attribute draws no second diamond: `ComboMultiplierDecorator` extends `ScoringDecorator`, which declares `inner` and carries the diamond to `IScoringPolicy`, and the subclass shows its `extends` and a use `«bind»` to `LinesScoring`. Any other attribute is a use with the attribute name and its multiplicity: a value object, the Strategy of a context, a port, the children of the Composite `ShapeGroup` and every other piece of a GoF pattern, because the class box already shows the attribute. The title of a frame names each pattern, and the interface of a pattern carries only `«interface»`. This is the form of the professor's solution of the exercise of 2026-11-06, which he handed out in the class of 2026-11-14, and the team took it on 2026-11-15 (decision 23). Every view follows it since #52. The hollow diamond of a decorator is the form of the class of 2026-11-23, and the views `engine-4-sources`, `engine-7-rules`, `uc-1-contract` and `map-3-usecases` draw it since 2026-11-24 (decision 23).
- No line starts or ends on a dashed frame. A map draws a line between two groups from the chip of the class that holds, calls or implements to the chip of the class it needs, with the same rule as a view: an attribute shows its name and multiplicity, for example `phase 1`, and any other use shows a verb, for example `CREATES`. A line from frame to frame would claim that every class of one group uses every class of the other. In the session of 2026-11-03 the professor asked about such a line: «todas esas usan los tres bloques de abajo, a lo mejor la respuesta es no». A map draws only the main dependencies, one or a few for each pair of groups. The view of each group shows the rest.
- The legend of each view lists only the line kinds that the view draws. A view lists `Composition` only when it draws a filled diamond, and `Aggregation` only when it draws the hollow diamond of a decorator.
- In the variant views, a lollipop (a circle on a short line) is an engine interface that the class implements. Its label names the type that each parameter takes, for example `IGameRules‹PlacePiece, LinesState›`.
- In a map, a chip is one class with its name only. Every line of a map starts and ends on a chip. The group header names the view that shows the members, for example `VIEW 2`.
- In the variants map, a dashed chip is an engine type. Each class in its row implements or extends it.
- A dashed box with no members is a class that another view details. Its eyebrow names that view, for example `PART 1 · VIEW 1`.
- Under the name of a use case, an ID such as `APP-FR-08` names the requirement it serves.
- `UseCase` and `UseCaseAspect` name architecture roles, not game concepts. `UseCase` is the generic input port, the «input boundary» of Clean Architecture, and every use case implements it (decision 9). `UseCaseAspect` is the abstract base of the AOP decorators of view 3.1. APP-NFR-11 asks one aspect to cover the four variants, so all use cases need one shared contract, and its name states that role. The professor's rule «Tiene que tener semántica del problema» (class of 2026-10-16) applies to the entities, the concrete use cases and the ports, and they follow it: for example `ApplyMove`, `MoveHistory` and `GameRepository`.
- `«port»` marks an interface of layer 2 that an outer layer implements. Ports live in the application layer (decision 25). The engine and layer 3 have other interfaces that an outer layer implements, such as `Clock`, `KeyValueStore` and `HealthApi`. They carry `«interface»` only. `«aggregate root»` marks the entity that guards a game (decision 26). `«value object»`, `«entity»`, `«aggregate root»`, `«domain event»`, `«factory»` and `«repository»` are the tactical stereotypes of the domain design. A factory box carries `«factory»`, next to `«interface»` on an interface such as `GeometryFactory`, and no role label: the title of its frame names its design pattern, for example `HexGeometry` in the `ABSTRACT FACTORY` frame of view 6. A repository port carries `«repository»` next to `«port»`, and a repository adapter carries `«repository»` only. A box with no tactical stereotype is a piece of a design pattern: the title of its frame or a note of the view names the pattern (decision 23). `GameRepository` carries `«repository»` next to `«port»`: it is the repository of the game aggregate (decision 10). A question in the stereotype line, such as `«composition root» · Q9`, marks a placement that the professor's answer can move. The screens, such as `GameScreen`, and `BoardView` are React components of layer 4, not classes. No box carries a label for it: a note of each view that draws one says so.
- The code holds the engine in `src/domain/engine/`, its shared leaves in `src/domain/shared/`, the progress and the levels in `src/domain/progress/` and the achievements in `src/domain/achievements/` (decision 64), the four variants in `src/domain/variants/`, of layer 2 `StartGame`, `ApplyMove`, `UndoMove`, `RedoMove` (#178), `SaveProgress`, `LoadProgress` (#181), `LoggingAspect` and their ports in `src/application/`, of layer 3 `InMemoryGameRepository`, `GameEventBus` with `GameEventListener` and `AchievementCounterListener` (#362), `LocalProgressRepository` (#164) and `LocalAchievementCounterRepository` (#363) in `src/adapters/`, and of layer 4 `CompositionRoot`, `GameRegistry`, `BoardFigure` (#171), `SystemClock`, `SeededRandomSource`, `ConsoleLogger` and `SequentialMatchIds` in `src/infrastructure/` (#162), the driver interface `KeyValueStore` in `src/adapters/` and its driver `DeviceKeyValueStore` in `src/infrastructure/` (#155), and `BoardView` and `CellRenderer` in `src/infrastructure/board/` (#165), with `BoardLayout`, `HexLayout`, `SquareLayout` and `TriangleLayout` of layer 3 in `src/adapters/board/` (#165, #393), and `ApiClient` in `src/infrastructure/api/`, which implements `HealthApi`, the transport interface of layer 3 in `src/adapters/api/` (#404). A class with a `«Sprint N»` stereotype is planned. View 2 draws two members that the code adds: `GridTopology.key(c: TCoord): CoordKey`, because the board stores its cells by a key, and a `contains: (c: TCoord) => boolean` parameter on `GridTopology.line()`, so the topology stops the line at the edge of the board. `Board.contains(c: TCoord): boolean` exposes the same test. `Board.line()` through a coordinate outside the shape yields nothing. The `Board` constructor throws a `RangeError` for an initial entry outside the shape and for an entry whose key differs from `GridTopology.key()` of its coordinate. It copies each entry, so the caller and the board share no tuple. `Piece.translated(offset: TCoord, topology: GridTopology<TCoord>): Piece<TCell, TCoord>` moves the shape through `ShapeNode.translated()`, so the triangle test of decision 16 can translate a piece. Issue #86 closes the primitive types of view 2 (APP-NFR-25): `GridTopology<TCoord, TAxis extends string, TDirection extends string>` and `Board<TCell, TCoord, TAxis extends string>` carry the closed axis and direction unions of each topology, `ring()` takes a `Radius` (a whole number of zero or more), `region()` a `RegionSize` (a whole number of one or more), `rotate()` and `rotated()` a `Turns` (any whole number). Each `of()` accepts only a safe integer (`Number.isSafeInteger`) and stores `-0` as `0`, and `key()` returns `CoordKey`, a value object since #246 (decision 44). Since #207 an axis and a direction are classes with a closed set of instances (decision 45), and `TAxis` and `TDirection` default to `GridAxis` and `GridDirection`. `Board` and the shape operations take a topology with any direction, and `BoardSnapshot.board` is a `ReadonlyBoard<TCell, TCoord>`, a board with any axis, so `GameEngine`, `IGameRules` and `BoardState` gain no type parameter. Since #416 `GridTopology` names no direction: `TDirection`, `GridDirection`, `neighbor()` and `directions()` are gone, and each topology keeps its direction class private (decision 16). The README table «Primitive types» gives the reason for each primitive that stays. `GamePhase.resume(): GamePhase` ends a pause. A phase keeps its name private: `GamePhase.checkAcceptsMove(): void` and `checkAcceptsUndo(): void` throw the `RangeError` that names the phase when the phase refuses a move or an undo, so `GameEngine` does not read the name. `Resolution` is a value object that holds an `accepted` flag and the `Outcome`, and no state: `equals()` compares both values (decision 26), and `Outcome` is a value object with the closed set of instances `playing`, `victory` and `gameOver` (decision 45). `GameEngine` takes its `MatchId` and its `GameId` in the constructor, answers its phase through `currentPhase()`, has `resume()`, and takes an optional history, an `IUndoable`, for undo (APP-FR-08, decisions 3 and 27) and an optional timer (decision 19, #234). It takes no `GameEventPublisher`: it records its events, and `ApplyMove` takes them with `takeEvents()` and delivers them (#233). `SeededPieceSource` takes a `Seed` and builds its own `Mulberry32Random` with `Mulberry32Random.from(seed)`, an engine `RandomSource` with the Mulberry32 generator, so the same seed gives the same pieces. A source is a value object: `take()` returns the piece and the next source, and no operation changes the source (decision 51). `Mulberry32Random` has `clone()`, which copies the generator state (decision 31). A `Seed` holds an integer from 0 to 4294967295, and `Seed.of()` throws a `RangeError` for any other number, so no seed is truncated into another (decision 48). `FixedListPieceSource` throws a `RangeError` on a list that holds `undefined`, and it copies its list once and freezes the copy. `IRandomSeeded` keeps its `Seed` private, and `isSeededWith(seed)` tells whether the object draws from a seed (#234). `BaseGameRules` adds the protected step `noValidMove(state: TState): boolean`, the end check of decision 33, so each variant `evaluate()` reuses it. `ProgressRecord` keeps the `GameId` and the `Score` of a result, and the record of a level also keeps its `LevelId`, `Stars`, `Moves` and `ElapsedTime` (decision 56). Its fields are private, and `deliverTo()` gives them to a repository of the edge (decision 57). `GameResult.of()` and `ProgressRecord.of()` take value objects, and each value object checks its own value: `Score.of()`, `Stars.of()`, `Moves.of()` and `ElapsedTime.ofMs()` throw a `RangeError` for a number that is not a safe integer of 0 or more (decisions 41 and 42).

## Decisions to check with the team

Decisions 41 to 49 planned the units of the domain redesign, and each one names the issue that brought it to the code. All nine are as built since #211, the last one: no decision of this list is planned. A class or a member that is still planned carries a `«Sprint N»` stereotype in its view.

1. **Template Method by composition.** Replaced by decision 21 on 2026-10-30. This draft kept the skeleton in `GameEngine.play()` and took the steps from `IGameRules` (Strategy), so a variant never extended a base class. The professor may expect the inheritance form of §3.3, with an abstract turn class and one subclass per variant.
2. **`GamePhase`, not `GameState`.** The State pattern classes are phases, because `TState` already names the state of a game. [layers.md](layers.md) uses the same name.
3. **Undo is optional per variant.** `GameEngine` holds zero or one history, an `IUndoable` (decision 27), and the variant factory decides. Fit gets `RedoableHistory` with no limit, Merge gets `MoveHistory` with limit 1, and Lines and Sort get none. So Hexa Lines never implements `IUndoable` (§3.2). Since #243 the limit is an `UndoLimit` in `src/domain/engine/undo-limit.ts`, not a number: `UndoLimit.of(value)` takes a safe integer of one or more and throws a `RangeError` for any other number, `equals()` compares two limits, and `newestOf(items)` gives the newest items that the limit keeps. The constructor of `MoveHistory` takes the optional `UndoLimit` and makes no check, and `MergeFactory` passes `UndoLimit.of(1)`. Since #178 `FitFactory` gives a `RedoableHistory` in `src/domain/engine/redoable-history.ts`, with no limit, so Fit undoes and redoes every move. `RedoableHistory<TMove, TMemento>` extends `MoveHistory` and keeps each undone `MoveCommand` in its private `undone` list, newest last. `MoveHistory.undo()` gives each undone command to its protected hook `keepUndone(command)`: a plain history forgets the command, and `RedoableHistory` keeps it. `redo()` plays the newest undone command again and puts it back among the done commands, so an undo can take it back again. A refused redo keeps the command, as a refused undo does. `record()` and `clear()` forget the undone commands: a new move, a new game and a finished game start another line of play, and a redo after them would give back a board of the old line. The root is the only door to the history: a caller asks `GameEngine.undo()`, `redo()`, `canUndo()`, `canRedo()` and `offersUndo()`, and the root asks its history (decision 27, #234). Since #179 the Merge game screen undoes one slide through the root: the undo button of `MergeControls` calls `GamePresenter.onUndo()`, `UndoMove` calls `GameEngine.undo()`, and the root asks its `MoveHistory` with `UndoLimit.of(1)`. The history keeps one move, so a second undo in a row finds none: the button takes no press, and `UndoMove` answers `nothing-to-undo` and changes nothing (APP-FR-08).
4. **`IRedoable` is our addition.** The statement lists `IUndoable`, `ITimed` and `IRandomSeeded`. Merge undoes one move and never redoes, so redo gets its own interface (§3.2 ISP, §5.1.8). `RedoableHistory` implements it, and its `redoable()` returns the history itself (#178). `RedoMove` in `src/application/redo-move.ts` asks the root, as `UndoMove` does: it asks `GameEngine.canRedo()`, returns a failed `Result` with the code `nothing-to-redo` when it is false, and then calls `GameEngine.redo()`. The root has no `offersRedo()`: a variant with no redo always answers `canRedo()` false, so `RedoMove` needs no other failure. A redo that the engine refuses, for example in a paused game, gives `redo-failed`, and a repository with no game gives `no-running-game`. A redo gives back the photo after the move (decision 34), so in Fit an undo and then a redo give back the same board, the same score and the same move count (APP-FR-08). The root still has no `offersRedo()` after #179. The view model of Merge keeps a `redo` entry that is never enabled, and `MergeControls` do not draw it, because the controls of each game choose their buttons (decision 55). A root query and a `MoveResult` flag for redo would change the answer of every game use case for one button that no screen shows.
5. **`Color` and `GameId` live in the engine.** Lines and Sort both use `Color`, and rule `variants-isolated` forbids one variant from importing another. `GameId` is open, so a new variant does not change it (decision 30). Since issue #129 the code holds it: `Color.of(name)` in `src/domain/engine/color.ts` rejects an empty or blank name with a `RangeError`, and `equals()` compares two colors by name, because `of()` makes a new object on each call. A Lines cell is a `Color`, and each tile of a Sort `ColorStack` is a `Color`.

An axis steps along itself from a cell with `forward()` and `backward()`, so a topology keeps no table of steps by name: `line()` asks the axis. The topology names no direction (#416, option A, decided on 2026-11-26). Until #416 `GridTopology` took a third parameter, `TDirection extends GridDirection`, for `neighbor()` and `directions()`, and only tests called them. A slide is an axis and a sense: Hexa Merge slides along `Slide.axis` with a `SlideSense`, and the triangle grid has 3 directions but 6 slide ways, so a direction cannot model a slide. Each topology keeps its direction class, `HexDirection`, `SquareDirection` or `TriangleDirection`, private to its file: a direction holds a step, and `neighbors()` asks its `neighborOf()`. So a new topology, such as triangular cells or a 3D board, writes no public direction class. `HexCoord` and `HexTopology` are only the hexagonal family (decision 17). `Board` is the `HexBoard<TCell>` of statement §3.1, which calls its names «orientativos». `TCoord` reaches `Piece`, `ShapeNode`, `BoardShape`, `BoardState` and the moves (`PlacePiece.at`, `PlaceStack.at`). `GameEngine` declares `TCoord` next to `TCell`, `TMove` and `TState`, and bounds `TState` by `BoardState<TCell, TCoord> & Cloneable<TState>` in its template box. `IVariantFactory`, `GameRepository` and the game use cases declare `TCoord` too, because their members name `Board<TCell, TCoord>`, `Piece<TCell, TCoord>` or `MoveResult<TCell, TCoord>`. `IGameRules` and `BaseGameRules` take two type parameters, `TMove` and `TState`: none of their members names a cell or a coordinate. The variant classes drop the `Hexa` prefix, for example `LinesRules` and `FitFactory`. `GridTopology` owns `rotate()`, `translate()` and `region()`, and the engine reaches a coordinate only through it. Since #206 the work has two owners (decision 44). A coordinate is a value object that does the calculations on its own values: it compares itself with `equals()`, and it gives its sum, its opposite, its distance, its turn of one step and its text. The topology does what belongs to the grid: the key, the neighbors, the axes, the lines, the rings and the regions, and the count of steps of a rotation. Adding two coordinates one component at a time works for hexagons and squares, so `HexCoord` and `SquareCoord` have `plus()`. It fails for triangles, because the parity of column plus row decides whether a triangle points up or down, so `TriangleCoord` has no `plus()`: it has `translated(offset)`, which counts lattice cells. With this rule, triangular cells and a 3D board (§8) each mean one more coordinate type and one more topology, plus new level data. In class on 2026-10-30 the professor asked for one generic board for hexagons, triangles and squares. The square topology cannot catch the parity coupling, because a square adds coordinates the same way a hexagon does. Issue #69 adds an engine test that translates a piece by an odd offset on the triangle topology. The type system also enforces the rule of issue #69. `TCoord` has no bound, so engine code cannot read a component of a coordinate and cannot call an operation of one: `c.q` and `c.equals()` do not compile there. Engine code must ask the topology for every calculation, and it compares two coordinates through `GridTopology.key()`. Issue #206 decided to keep `TCoord` without a bound. Team decision D10. 21. **Template Method in an abstract base class.** The abstract `BaseGameRules` implements `IGameRules`. Each variant rules class extends it. **The contract keeps two members (#413, option A-strict, decided on 2026-11-26).** `IGameRules` declares only `validMoves()` and `playTurn()`. `GameEngine` calls only `playTurn()`, so a contract with the four steps made the engine depend on members that it never uses (statement §3.2, ISP). `validMoves()` stays public, because statement §3.1 says that the rules define the valid moves, and decision 33 gives it a reader. The four steps are `protected abstract` in `BaseGameRules` and `protected` in the four variant rules classes: in the Template Method of GoF the primitive operations are protected, so only the template method calls them (statement §3.3). `TimedRulesDecorator` wraps the two members, and no test calls a step: the variant tests pin each outcome through `playTurn()` (statement §3.6). A rejected move never ends the game, and two guards enforce it. `Resolution.evaluated()` on a rejected resolution throws a `RangeError`, so a custom `playTurn()` that evaluates a rejected resolution fails, and `GameEngine.tryPlay()` rethrows that error with the state kept. For a rejected resolution that still carries a final outcome, `GameEngine.tryPlay()` returns a rejected resolution with the outcome `playing`, keeps the phase `playing` and publishes no event. The engine computes the next phase before it commits the turn. An outcome that the phases do not know throws a `RangeError`, and the state and the phase stay as they were. When a turn throws, the rollback covers the whole state and the phase. The piece source lives in the state (decision 31), and a draw replaces it only in the copy of the turn (decision 51). So a turn that is retried after a throw draws the same piece, and a move that `resolve()` rejects leaves the source at its old position. A `Resolution` holds no state, only `accepted` and the `Outcome`: the rules change the state that they receive in place, so the engine reads the copy that it gave them. `GameEngine` depends only on the interface `IGameRules`, so the Strategy of D1 stays, and a decorator such as `TimedRulesDecorator` can wrap any rules. 26. **`GameEngine` is the aggregate root of a game (proposal).** The aggregate holds the state with its board, the `GamePhase`, the optional history (an `IUndoable`, decision 27) and, in a timed game, the `LevelTimer`. The root is an entity, and a `MatchId` is its identity (decision 30). It takes the id in its constructor, and the id never changes. The state is an entity inside the aggregate, and it has its own identity, a `GameStateId` value object. The id is local (decision 52): `GameFactory` builds it from the `MatchId` of the root with `GameStateId.of(matchId)`. `BoardState.equals(other)` compares two states by that id only. The state also keeps the `MatchId` of its game: `GameFactory` gives the same `MatchId` to the engine and to `IVariantFactory.createInitialState(matchId, stateId, boardId)`, and `BoardState.belongsTo(match)` tells whether a state is the state of a match. A clone keeps both ids, because the clone is the same state at an earlier moment, and a move changes the state in place, so it keeps them too. `GameEngine.start()` throws a `RangeError` for a state of another match and keeps its old state. The `LevelTimer` of a timed game is an entity inside the aggregate boundary too (decision of 2026-11-09, #214). It has its own identity, a `LevelTimerId` value object that the timed variant factory builds from the `MatchId` in `createTimer(matchId)`, and `LevelTimer.equals(other)` compares two timers by that id only (decisions 19 and 50). The root keeps the timer as an optional part, as it keeps the history: `GameFactory` gives the same timer to the root and to the `TimedRulesDecorator` that the root holds as its rules (decision 19, #234). The decorator starts and stops it, and the root reads the time of play from it. So no caller outside the aggregate starts or stops the timer, and no caller gets it. The root is the only door to its parts (decision 52): `undo()`, `redo()`, `canUndo()`, `canRedo()`, `offersUndo()` and `elapsedTime()` answer for the history and the timer, and no method returns either part (decision 27). `Resolution` holds no state (a team decision of the domain redesign): it keeps whether the rules accepted the move and the `Outcome`, both in private fields (#240). It is a value object (decision of 2026-11-10 on #212): it is immutable, it has no identity, and `equals(other)` compares `accepted` and `outcome`. A reader asks a query with a business name: `wasAccepted()`, `endsTheGame()`, which is false for a rejected move, and `phaseAfter(phase)`, the phase that follows the turn. `BaseGameRules`, `TimedRulesDecorator`, the root and `ApplyMove` read a resolution only through these queries. `leadsTo()` returns the `Outcome` itself, because two readers need the value: the `GameEnded` event carries it, and `MoveResult.outcome` holds it (decision 29). No engine code compares two resolutions today; the stereotype follows the rule of the class of 2026-11-09, that every domain concept carries its tactical stereotype. Since #207 `Outcome` is a class with a closed set of instances (decision 45), so `Resolution.equals()` compares the two outcomes with `Outcome.equals()`. `equals(other)` compares two engines by that id, whatever their boards, scores and phases hold. `GameFactory` creates the root with the id of an injected generator, so the engine reads no random source and no clock for it (decision 40). Its invariant: a game changes only through `tryPlay()`, `undo()` and `redo()`, and each acts only while `currentPhase().canPlay()` is true. **One entry for a turn (#415, option A, decided on 2026-11-27).** `tryPlay(move): Resolution` is the only entry of a turn: `ApplyMove` calls it, and the `Resolution` says whether the rules accepted the move. Until #415 the root also had `play(move): Outcome`, which returned `tryPlay(move).leadsTo()`. No production code called it, and it hid a rejected move behind the outcome `playing`. So the root keeps one entry, and production code with no caller does not stay, for the reason that removed `NullGameEventPublisher` in #412. The tests read the outcome of a turn with the helper `playMove()` of `test/support/engine/play-move.ts`, which asks `tryPlay()`. `snapshot(): SnapshotOf<TState>` returns the immutable photo of the state (decision 34), so no caller changes the board outside the root. The root takes no publisher (#233). When it saves a turn that ends the game, it records one `GameEnded` event in a private list and tells nobody. `takeEvents(): readonly GameEvent[]` gives the recorded events in their order and empties the list, so a caller never gets an event twice. `GameEnded` extends the abstract `GameEvent`. **The name of the end event (#421, option A).** `GameEnded` reports the end of a game, a victory or a defeat, and a listener asks `isVictory()` to know which. Until #421 its name was `GameOver`. But «game over» also names two things that mean a defeat only: `GameOverPhase`, the phase after a defeat, and `Outcome.gameOver`, the outcome of a defeat. So a reader had to learn a third meaning of the same words. The event now takes a name that says only that the game ended, and «game over» keeps one meaning, a defeat. **The events of a move (#361, part 1 of #277).** When the root saves an accepted turn, it also records the events of the move, before the `GameEnded` of the same turn. The variant state keeps the facts of the last move, as it keeps `linesCleared`, `merged` and `clearedTiles`, and the root asks the photo after the move `BoardSnapshot.eventsOfLastMove(game: GameId, match: MatchId): readonly GameEvent[]` with its own two ids. The base photo gives no event, and each variant photo builds the events of its variant. So the root builds each event with its ids, it never imports a variant and never branches on the game id (rules R-engine-variants and R-engine-no-game-id), and the `Resolution` stays a value without facts. The three events live in their variant folders and extend `GameEvent`: `LinesCleared<TCoord>` (one per Lines placement that clears one line or more: the `LineCount` of the combo and the cleared cells in the order of the wave, the order in which the rules find the lines, each cell once; a count of no line throws a `RangeError`), `TileMerged<TCell>` (one per merge of a Merge slide, in the order of the merges: the tile that the merge made), and `StackCleared<TCoord>` (one per stack that a Sort turn clears, in the order of the clears: the cell and the `TileCount` height of the stack). One Sort goal is one cleared stack, as `ClearedStacks` counts it; `GoalCount` stays the goal of a level. Each event also keeps the `MatchId`, as `GameEnded` does. A rejected move records no event. An event is a fact that happened: an undo does not take it back and records no event, and a redo records none either, because only `tryPlay()` records events. A listener that counts events (#277) counts the move that the player later undid. No event carries the points of the move, the Sort transfers or the paths of a Merge slide: #293 and #294 add them when they need them, as new fields or new events. No variant names an achievement. Every field of an event is private: `GameEvent` keeps the `GameId` and gives it only to the delivery of a subclass through the protected `withGameId()`, and a listener asks `GameEnded.isVictory()` or receives the data through `GameEnded.deliverTo(receiver: GameEndedReceiver)`. Each event of a move gives its data the same way, through `deliverTo()` and a receiver interface next to it: `LinesClearedReceiver`, `TileMergedReceiver` and `StackClearedReceiver`. No code of layers 1 and 2 asks the class of an event, and neither does `GameEventBus`. Since #362 a listener of layer 3 may tell one event from another with `instanceof`, and it receives the data of an event through `deliverTo()`. Since #406 `AchievementCounterListener` asks no class: it asks `countsForAchievements()` of the domain, and each event that counts records its own count (decision 60). `ApplyMove` calls it after each turn (decision 29). `GameRepository` is the repository of this aggregate: it saves and gives back the whole root between two calls (decision 10). The scoring policy is the Strategy that the root holds (decision of 2026-11-15, #230): the root calls `IScoringPolicy.score(before, after)` and does not know the concrete policy. The policy computes points from two photos of the state and keeps no game data. The resolution stays in the rules, which call the business methods of the state (decision 7).     **Why this root and this boundary.** The class of 2026-11-14 asks the design to justify the root and the boundary of each aggregate, and `GameRepository` saves the whole root, so the boundary says what «whole» spans. `GameEngine` is the root because it is the only object that guards the invariant of a game: a game changes only through `tryPlay()`, `undo()` and `redo()`, and the root checks the phase before each change. Its `MatchId` is the identity of the whole aggregate in the system (decision 52). The state with its board and, in a timed game, the `LevelTimer` are inside the boundary, with the `GamePhase` and the optional history. They change together: one accepted turn changes the board, the score and the phase as one unit, and the turn that ends a timed game also stops the timer (decisions 19 and 21). They have no meaning outside their match: a state belongs to one `MatchId`, and its board and the timer live and end with that game. So the boundary is not smaller: a board or a state as an aggregate of its own would split one turn across two aggregates, and one transaction would change both. The progress of the player is outside the boundary. It is another concept of the business: it gathers the results of many matches, for example the stars of each level, and it has its own port, `ProgressRepository`. It changes after the game ends, in a transaction of its own: `SaveProgress` takes `GameResult`, the summary data of a match, and never an internal entity of the game. `GameResult`, `ProgressRecord`, `FitPlay` and `SortPlay` keep every field private (#240): a progress model asks `GameResult.recordWith()` for its record, and `GameProgress` asks `ProgressRecord.improves()` for the better record (#156), and a star threshold asks the play `isWithin()` (decision 42). So the boundary is not larger: an aggregate that held the progress would put two concepts of the business in one aggregate, and each move of one match would also change the record of every match of the player (decision 52).

27. **The root answers for its capabilities (#234).** The class of 2026-11-13 makes the root the only door of the aggregate (decision 52), so the root hands out neither its history nor its timer. `GameEngine.undo()` and `redo()` act through the capabilities that the variant factory gave, and `canUndo()`, `canRedo()` and `offersUndo()` answer the questions of a use case. `offersUndo()` tells whether the variant has undo at all, because a false `canUndo()` cannot tell «no undo» from «undo used». `undo()` throws a `RangeError` for a game with no history, and `redo()` throws one for a history that cannot redo. `UndoMove` asks `offersUndo()` and `canUndo()`, returns a failed `Result` when one of them is false, and then calls `undo()`. `RedoMove` asks `canRedo()` and calls `redo()` (#178). So no use case reads a history or names its class, and a new history type changes no use case. Inside the aggregate the capabilities stay: `MoveHistory` implements `IUndoable`, and `MoveHistory.redoable()` gives the `IRedoable` of a history that can redo, so the root reads the redo with no check of the history class. **The root depends on `IUndoable` (#414, option A, decided on 2026-11-26).** `IUndoable<TMove, TMemento>` declares the five members that the root calls: `record()`, `clear()`, `canUndo()`, `undo()` and `redoable()`. `GameEngine` keeps its history as an `IUndoable`, and `IVariantFactory.createHistory()` returns one, so neither names the class `MoveHistory`. The high-level policy depends on an abstraction, not on a concrete class (Martin, Clean Architecture, ch. 11, DIP). Statement §3.2 asks for `IUndoable` as a separate capability, and after #234 nothing read the interface: it declared only `canUndo()` and `undo()`, and the root also needs `record()` and `clear()` to keep the moves of a turn and to forget them. So the name of the statement carries `record()` and `clear()` too. `IRedoable` stays apart, because Hexa Merge undoes and never redoes (decision 4). `GameEngine.elapsedTime()` does the same for the timer: it returns the `ElapsedTime` of the timer that the variant factory gave, or `undefined` for a game with no timer (decision 19). Until #234 the root returned the capabilities through `undoable()`, `redoable()` and `timed()`, and `IGameRules.timed()` gave the timer of the rules. Views 1, 3 and 3.2.
28. **Use cases return a `Result`.** In Clean Architecture an exception must not reach the screen. `UseCase.execute(request: TRequest)` returns `Promise<Result<TResponse>>`. `Result<T, E = UseCaseError>` holds a value or an error, and `Result.success(value: T)` and `Result.failure(error: E)` create it. `UseCaseError` has a `code` of type `FailureCode` (decision 62), a `message`, a `retryable` flag and an optional `cause`. An empty or blank `code` throws `RangeError("A use case error needs a code.")`, because the presenter picks its message by the code (G117.6). `caughtError(code, thrown)` builds the error of a caught exception and keeps the thrown value as its `cause`, so the log still shows a programming error. It never throws: a thrown value whose text `String()` cannot build, such as `Object.create(null)`, gets the fixed message «The thrown value has no text.» and stays the `cause` (issue #138). `RetryAspect` runs the use case again while the error is retryable, and the presenter shows the message through `GameViewModel.error`. Since issue #132 no aspect breaks this promise: `UseCaseAspect.execute()` turns every exception, from the inner use case or from the aspect's own work such as a logger that throws, into a failed `Result` with the code `unexpected-failure` (G118.1, G118.2). An aspect puts its concern in the protected `around()` and calls `super.around()` to run the inner use case, which gives an `unexpected-failure` `Result` when the inner promise rejects. A failed `Result` of the inner use case passes through unchanged. Decision 62 lists the failure codes. `publish-failed` is the one code that never fails a call: it travels inside a success, in `MoveResult.failedDeliveries` (decision 29). Views 3.1, 3.5 and 4.1.

52. **The rules of an aggregate and of a domain service.** They come from the classes of 2026-11-13 and 2026-11-14, and the team took them on 2026-11-15. They hold for every aggregate of the app: the game aggregate of decision 26 and any later one. Where the code of today does not follow a rule yet, the rule names the issue that changes the code. The decision that describes the code of today stays as it is until that issue lands.
    - **One unit of change.** An aggregate is a group of entities and value objects that changes as one unit. It is not a collection. After each operation on the aggregate, all its invariants hold, and the aggregate is also the limit of one transaction.
    - **Only the root is reachable.** Code outside the aggregate talks only to the root, and the root is the facade of its parts. No public method returns an internal entity or another aggregate: data leaves the aggregate as summary data, never as an internal entity.
    - **Global identity only in the root.** The root is an entity, and its identity is unique in the whole system: the `MatchId` of the game aggregate. An internal entity has a local identity: its id has a meaning only inside its aggregate. So `GameFactory` builds the `GameStateId` and the `BoardId` from the `MatchId`, and a timed variant factory builds the `LevelTimerId` from it (decisions 7, 26, 40 and 50).
    - **Entities and value objects.** An entity compares with `equals()` by its id only, whatever its other fields hold. A value object has no identity: it compares with `equals()` by all its attributes, and it never changes, so each operation returns a new value object. This is the rule of the class of 2026-11-09, and the code follows it.
    - **One repository per aggregate.** Each aggregate has its repository in the design, also when its implementation keeps the data in memory. The repository saves and gives back the whole root, and no internal entity has a repository. The repository of the game aggregate is `GameRepository` (decision 10).
    - **One aggregate per transaction.** One transaction changes one aggregate. Another aggregate takes the change later, so the design accepts eventual consistency outside the boundary. An operation that must change two aggregates at once shows a boundary in the wrong place.
    - **References by identity.** An aggregate refers to another aggregate only by the system id of its root, never by the object and never by a business key that can change. An aggregate can keep a local view with only the data that it needs from another aggregate. `GameId` is not such a reference: it names a variant of the catalogue (decision 30), and the catalogue is not an aggregate. If the catalogue becomes an aggregate, a reference to it uses a system id. `GameProgress` is an aggregate whose identity is the `GameId` of its game, because the device keeps one progress per game: its `equals()` compares only that id. `GameId` is a business key, but the reason of the rule holds: the team fixes each `GameId` in the code, and no user changes it. This identity stops being enough when an account owns progress (D27 in [REQUIREMENTS.md](../REQUIREMENTS.md)): then a progress belongs to a user in a game. #46 decides then whether the identity becomes its own value object.
    - **Events, not questions.** An aggregate never asks another aggregate. It tells its changes through a domain event: it only emits the event, to nobody in particular, and each listener reacts (Observer). The game root records its `GameEnded` event and tells nobody, and `ApplyMove` takes the event after the turn and delivers it to the publisher port (decisions 25, 26 and 29).
    - **Small and cohesive.** A value object is never a root. Two concepts of the business never share one aggregate. Cohesion decides the size of an aggregate, not a count of classes. An entity becomes an aggregate of its own only with a written reason. The game aggregate holds the parts of one match, and the history and the timer are optional parts that the variant factory gives (decision 3).
    - **The boundary in the diagram.** The class diagram shows the boundary of each aggregate. The form of the line does not matter. View 1 and the map of Part 1 draw the game aggregate as a dark dashed frame labelled `AGGREGATE · DECISION 52`, so it differs from the grey frame of a pattern (#21). The frame holds the root and its internal entities: `GameEngine`, its `BoardState`, the `Board` of the state and the `LevelTimer` of a timed game. Each internal entity has a local id. View 1 shows the board and the timer as reference boxes, and the map gives the four classes a group of their own. In view 1 the root joins the state and the timer with a filled diamond (decision 23). The state keeps the board, not the root, so a use `board 1` joins them inside the frame. The `GamePhase`, the optional `MoveHistory` and the two Strategies are parts of the aggregate too (decision 26), and each one is a piece of a pattern: it stays in the frame of its pattern, and the root keeps it with a use.
    - **Domain services.** A domain service is a business operation of the domain layer that belongs to no entity, value object or aggregate. First give the responsibility to an aggregate. It leaves the aggregate only when the code must load other aggregates or create objects of another aggregate. A domain service exposes one public method that validates or computes, and it can use private methods. It takes and returns domain objects. It keeps no state, and it guarantees a result, not an invariant. It receives the objects already loaded and never calls a repository. It never touches the infrastructure: a message to a player is the work of an application service. Its name and its method are verbs of the ubiquitous language, never a `Helper` or a `Manager`. It can work with another domain service. It replaces no entity: the rules of each aggregate stay inside the aggregate. A use case is an application service, not a domain service. A Strategy that the root holds is a piece of the aggregate, not a domain service (decision 26). The domain has no domain service today.
