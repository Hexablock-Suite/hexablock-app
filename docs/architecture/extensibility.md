# Extensibility diagram

Status: draft for review with the team, 2026-10-31.

Statement §4.3 asks for a «Diagrama que muestre el motor genérico en el centro y las cuatro variantes como extensiones, resaltando los puntos de extensión (interfaces que una quinta variante debería implementar)». This page answers it for the client in four views. View 1 is that diagram. Views 2 to 4 show the other extensions that the requirements declare: the jury variations, the geometry family and the extension points outside the engine. Class names come from the [class diagram](classes.md). IDs such as D4 and APP-NFR-06 refer to [`docs/REQUIREMENTS.md`](../REQUIREMENTS.md). [`docs/EXTENSIBILITY.md`](../EXTENSIBILITY.md) gives the file-by-file steps that APP-NFR-06 asks for.

## How to read it

- The colored zone is the Clean layer, with the colors of [layers.md](layers.md). The outer layer is at the top and the inner layer is at the bottom, so every dependency points down.
- The teal class is the generic engine. It knows no variant and no geometry (APP-NFR-03).
- A dashed frame groups one extension axis or one pattern. Its label names the source and, when the frame holds one, the pattern.
- The title of a frame or a footnote of the view names each pattern. No box carries a role label of a pattern: the interface of a pattern carries only `«interface»`, and a concrete piece of a pattern carries no role label (decision 23).
- A solid box is a class. A dashed box is a declared extension with no class yet. Its name is a placeholder.
- `«Sprint N»` marks planned design that the code does not have yet. N is the sprint that [`docs/ROADMAP.md`](../ROADMAP.md) gives to the requirement that the planned class serves. The view source names that requirement in the `data-requirement` attribute of the marker text, for example `data-requirement="APP-FR-16"`, and lists several IDs with a space between them. The image does not show the attribute. `test/docs/sprint-markers.test.ts` fails when a marker names no requirement or a requirement of another sprint. A planned class that serves no requirement of the roadmap carries no marker. A planned class or package carries the marker once, in its header, and the marker covers its members and arrows. A planned member of an existing class carries the marker on its own line. A dashed box with no marker has no sprint yet.
- A package (a box with a tab) is one variant folder. It lists the classes of that variant. An outlined name inside a package is the class that a line starts from.
- No line starts or ends on a dashed frame or a package. A line between two groups joins the two classes that depend, for example `LinesFactory` and `IVariantFactory`. A line from a frame or a package would claim that every class of one group uses every class of the other. In the session of 2026-11-03 the professor asked about such a line: «todas esas usan los tres bloques de abajo, a lo mejor la respuesta es no». When every variant has the same line, the view draws it for one variant and says so, for example «LINES AND MERGE STAND FOR EACH VARIANT».
- A list box names several classes of one kind, for example the local adapters.
- A realization arrow points from an extension to the contract it implements. A solid line with a hollow triangle is inheritance.
- A solid line with an open arrow is a use: an attribute, a parameter, a return value, a local variable or a `new`. Every dependency between two layers is a use. For an attribute, the arrow end shows the attribute name and its multiplicity. Otherwise the label is a verb, for example `PASSED TO`.
- A filled diamond goes only from an aggregate root to an internal entity of its aggregate, with its multiplicity (decision 23). No view of this page draws the composition of a root with an internal entity, so no view draws a diamond. A hollow diamond joins a decorator to the type that it wraps, with the label `decorate 1` (decision 23, change of 2026-11-24), and no view of this page draws that pair. Every other attribute is a use with the attribute name and its multiplicity, also when it is `1`, a piece of a GoF pattern included, because the class box already shows the attribute.
- The legend of each view lists only the line kinds that the view draws.
- The dashed box at the top right of a class holds its type parameters (UML template notation). A bound on a parameter goes in the same box, never on a line.
- Every operation shows the type of each parameter and its return type. View 1 abbreviates the type arguments of attributes and return types, for example `IGameRules` for `IGameRules<TMove, TState>`, except `createBoard(): Board<TCell, TCoord>`, and leaves out `isFor(gameId)` and `createTimer(matchId)` of `IVariantFactory`. In every view, the corner box of `GameEngine` leaves out the bound of `TState`. The views of the [class diagram](classes.md) show them in full.

## View 1: the extension points

The engine sits in the center of layer 1. Around it are the interfaces that a fifth variant implements, and the type arguments that it binds. The four variants of the statement and Hexa Fill, the example of §3.1 («por ejemplo, Hexa Fill: pintar celdas con restricciones»), implement them. Each variant also adds a state mapper in layer 3 and a cell renderer in layer 4 (D3). The variant factory creates the rules, the piece source, the scoring policy and the board (decision 31). `GameId` is open: each factory declares its own id, so a fifth variant changes no engine file (decision 30, D15).

In the defense the jury proposes «un nuevo tamaño de tablero, una política de puntuación distinta o una nueva forma de pieza» (§3.1). Each change is new data or a new class, and the engine does not change (APP-NFR-06). The section «The three jury variations» of [`docs/EXTENSIBILITY.md`](../EXTENSIBILITY.md#the-three-jury-variations) gives the steps of each one, with the tests and the documents that change with it.

## View 3: the geometry axis

A new geometry adds one family: a coordinate type, a topology and the piece shapes (decision 17, D11). It adds one instance to the closed set of `TopologyId` in `src/domain/shared/topology-id.ts`, which decision 45 keeps closed (#207), and it changes no other engine file and no variant. `HexGeometry`, `SquareGeometry` and `TriangleGeometry` are the three real families, one for each board figure that the player chooses (APP-FR-16), and the engine tests run on the square and triangle families (D4, APP-NFR-13). A 3D board is a declared variation in §8 of the requirements. Each variant factory receives a `GeometryFactory`, so a new geometry needs no class for each game, and a new game needs no class for each geometry. No line touches an axis frame. Each variant factory implements `IVariantFactory`, which creates the `IGameRules` that `GameEngine` keeps as `rules`. Each variant factory also keeps a `GeometryFactory` as `geometry`: the line from `MergeFactory` stands for all four. `HexGeometry`, `SquareGeometry` and `TriangleGeometry` implement `GeometryFactory`. No line joins a variant class to a geometry class, because a variant factory keeps the engine interface `GeometryFactory`, not a geometry class.

## View 4: outside the engine

Layers 2 to 4 have their own extension points. The view shows only the ones that §8 or the class diagram declare.

- **Database and backend.** A new storage or backend is one more adapter of the layer 2 ports. The use cases do not change (§3.3, §3.4, decision 22).
- **Level origin (A6).** `BundledLevelRepository` and `ApiLevelRepository` both implement `LevelRepository`, so bundled levels work offline (APP-FR-15).
- **Observer.** A new subscriber implements `GameEventListener` and subscribes to `GameEventBus`, which implements `GameEventPublisher`, the port of layer 2. The engine records its events, and `ApplyMove` delivers them to the port after each turn (#233).
- **Aspects.** A new aspect extends `UseCaseAspect` and wraps any use case (§3.5, APP-NFR-11).
- **The game registry.** `GameRegistry` of the composition root lives in layer 4, `src/infrastructure/game-registry.ts` (#162). It keeps one `RegisteredGame` per game, with its variant factory and its screen parts: the state mapper, the cell renderer, the move controls (#175) and the figure layout (#170). So a fifth variant adds one entry and changes no other class. The root builds one registry for each board figure that the player can choose (#171), so the entry of a fifth variant runs on every figure.
- **Desktop and a game with no board (D5).** Both are planned seams with no class yet. A game with no board needs a `GameModule` contract that a registry entry can hold, and the layer of that contract is open.

![Outside the engine: local and HTTP adapters in layer 3 implement the output ports of layer 2, ApiClient in layer 4 is the driver of the HTTP adapters, with the two level origins of A6; GameEventBus implements GameEventPublisher, the port of layer 2, and AudioManager listens to it; the aspects extend UseCaseAspect; GameRegistry in layer 4 keeps its RegisteredGame entries; the declared DesktopLayout, GameModule, NewStorageAdapter, NewListener and CachingAspect are placeholders](extensibility/views/ext-4-outer-layers.png)

Every name in the Fill column is a placeholder, because Hexa Fill has no class yet. The exceptions are `HighScoreProgress` and `LevelProgress`, which live in the engine. The team decides later whether Hexa Fill has levels, a piece source or undo.

The move controls live in `src/infrastructure/ui/`: `LinesControls` in `lines-controls.tsx`, `FitControls` in `fit-controls.tsx`, `SortControls` in `sort-controls.tsx` and `MergeControls` in `merge-controls.tsx`. `src/infrastructure/registered-games.ts` gives each game its controls (#174 to #177). The controls send a plain intent and import no class of a variant. The move mapper of the game in `src/adapters/` turns that intent into the `TMove` of the variant (#405, decision 14 of [classes.md](classes.md)).

The `TState` of a variant implements `BoardState`: it is an entity with its own `GameStateId` that keeps the `MatchId` of its game, and it changes in place only through its own business methods, so `FillState` would bring its own methods and its rules would call them (decisions 7 and 26 of [classes.md](classes.md)). `createInitialState(matchId, stateId, boardId)` gives the first state its two ids and its board the `BoardId`.

The capability classes `MoveHistory`, `RedoableHistory`, `LevelTimer` and `SeededPieceSource` live in the engine. A variant does not write them: its factory picks them (decision 3), and the root answers for them with `undo()`, `redo()`, `canUndo()`, `canRedo()`, `offersUndo()` and `elapsedTime()`, so no use case gets a capability (decision 27, #234). `LevelTimer` is an entity with its own `LevelTimerId`, so a factory that picks it builds that id from the `MatchId` that `createTimer(matchId)` takes, as `FitFactory` does (decisions 50 and 52). `HighScoreProgress` and `LevelProgress` live in the engine too, and `createProgressModel()` picks one. A variant with levels gives `LevelProgress` its level, which counts the stars of a play: a level with no timer implements `IStarsByMoves` and goes to `LevelProgress.byMoves()`, as `SortLevel` does, and a timed level implements `IStarsByMovesAndTime` and goes to `LevelProgress.byMovesAndTime()`, as `FitLevel` does (classes.md decision 36, #424). Its thresholds implement `IStarThreshold`, and `starsOf()` counts them. A piece source is a value object: a variant that writes its own `IPieceSource` gives `hasNext()`, `take()`, which returns the piece and the next source and changes nothing, and the iterator, which the engine function `piecesFrom()` gives (decision 51).

## Render the images

The views come from the HTML files in [`extensibility/views/`](extensibility/views/). They follow the same rules as the class diagram: open a file in a browser to see the drawing, and export the `.png` image again after each edit with `/diagram-design:export-diagram docs/architecture/extensibility/views/<view>.html --png-only`. Commit each `.html` file together with its `.png` image.
