Statement §4.2 asks for four concentric layers. The diagram draws them as four rings: layer 4, frameworks and drivers, outside, and layer 1, entities, in the center. Every arrow goes from the part that imports to the part it imports. No arrow points out, toward an outer layer. Some arrows stay inside one layer, for example from the use cases to the ports.

- Each ring is one layer. Colors: layer 1 yellow, layer 2 purple, layers 3 and 4 blue. The course colors three layers: the domain yellow, the application purple and the infrastructure blue. With four layers, layers 3 and 4 together are the blue infrastructure, so the team draws layer 3 light blue and layer 4 dark blue. The class views use the same colors.
- The ports sit on the edge of layer 2. A port is an interface that layer 2 owns and an outer layer implements, because a use case may depend only on ports of its own layer (§3.4). `UseCase` is the generic input port: the presenters call it, and every use case and every aspect implements it (decision 9 of the class diagram).
- A box is a class, a port or a group of classes. Its header names its folder or its kind. An adapter of layer 3 sits above the port that it implements.
- The engine owns `Clock`, `RandomSource` and `MatchIdGenerator`, and layer 3 owns `KeyValueStore`. A driver of layer 4 implements each one, but they are interfaces of their own layer, not ports (decision 25 of the class diagram).

A use carries a verb, such as `creates`, where the line is not the import of a contract. ## The rule of layers 3 and 4

The role of a class decides its layer. The examples in the table below follow this rule. The app and hexablock-api share it: it is option C of [hexablock-api#212](https://github.com/Hexablock-Suite/hexablock-api/issues/212), decided on 2026-11-26 and merged in Hexablock-Suite/hexablock-api#231.

- **Layer 3, `src/adapters/`:** every class that implements a port of layer 2, and the other code that the team writes to convert data between the form of the use cases and the form of an outside technology. Examples: presenters, view models, state mappers, the move mappers that turn the intent of a move control into a domain move (#405), repository and gateway implementations, the HTTP repositories, DTO mappers, DTOs, the transport interfaces of the HTTP client and the screen layout of a board figure (`src/adapters/board/`, #393).
- **Layer 4, `src/infrastructure/` and `app/`:** the frameworks and the glue code only. The routes and the React Native components of the screens. The drivers: the implementations of the interfaces that layer 3 or the engine owns, such as `DeviceKeyValueStore` for `KeyValueStore`, `ApiClient` for the transport interfaces of `src/adapters/api/`, and `SystemClock`, `SeededRandomSource` and `SequentialMatchIds` for `Clock`, `RandomSource` and `MatchIdGenerator` of the engine. The configuration and the composition root. No class of layer 4 implements a port of layer 2.
- **Layer 3 imports no package and no Node module.** A conversion that needs a library talks to an interface that layer 3 owns, and layer 4 implements it. For example, `LocalProgressRepository` uses `KeyValueStore` of `src/adapters/key-value-store.ts`, and `DeviceKeyValueStore` implements it with AsyncStorage. Rule `adapters-imports-only-inner-layers` checks this. `test/gates/architecture-gate.test.ts` tests it with a driver import and with a package import. Layer 4 keeps no import rule: its role, not its imports, defines it.

**The HTTP repositories live in layer 3 (Q7, option A3, #404).** `ApiProgressRepository`, `ApiLevelRepository`, `ApiLeaderboardGateway` and `ApiAccountGateway` implement ports of layer 2, and `ApiDtoMapper` turns their DTOs into domain values, so they live in `src/adapters/api/`. They are planned: #45, #46, #47 and #48 build them in that folder. Three parts keep them free of the HTTP library:

- `pnpm api:generate` splits its output into two files. `src/adapters/api/dto.d.ts` holds the DTO schemas of the backend OpenAPI document, so layer 3 owns the DTO types. `src/infrastructure/api/schema.d.ts` holds the paths and the operations, and it imports the DTO types. `pnpm api:check` compares both files with the backend.
- Layer 3 owns one transport interface per resource of the backend, in `src/adapters/api/`. Its methods take and give DTO types, never a type of `openapi-fetch`. It is not a port: layer 2 never sees it. Today `HealthApi` covers the health resource.
- `ApiClient` of `src/infrastructure/api/client.ts` is the driver: `createApiClient()` implements each transport interface with `openapi-fetch`. A change of HTTP library rewrites `client.ts` only.

No port of layer 2 names a DTO type, so no use case knows the shape of the HTTP data. The rule has no exception.

**Two classes of layer 4 do not follow the rule yet.** `ConsoleLogger` in `src/infrastructure/console-logger.ts` implements the `Logger` port, and the planned `SessionManager` implements the `SessionStore` port. By the rule both belong to layer 3. No gate checks the rule in the app: hexablock-api checks it with its rule `infrastructure-imports-no-port`.

## Where each piece lives

- **Generic engine:** layer 1, `src/domain/engine/`. `Board<TCell, TCoord, TAxis>`, `GameEngine<TCell, TCoord, TMove, TState>` (D1) and the contracts `IGameRules`, `IPieceSource<TPiece>` and `IScoringPolicy<TState>`. The shared implementations of the piece source (seeded or fixed) live here too. The contract `IProgressModel` and its two models (high score, or levels with stars) live in the sibling folder `src/domain/progress/`, and the achievements in `src/domain/achievements/`. The leaves that every folder names, such as `GameId` and `Score`, live in `src/domain/shared/` (decision 64). They take time and randomness through the `Clock` and `RandomSource` interfaces of the engine. `GameEngine` is the aggregate root of a game: a game changes only through `play()`, and `play()` applies a move only while the phase allows it. The state of the game is an entity inside the aggregate: it has an id of its own, and it keeps the `MatchId` of its game. The rules change it only through its business methods, and the engine adds the points with `BoardState.addPoints()` (decisions 7 and 26). The scoring policy is the Strategy that the root holds (decision 26). The geometry family (`GeometryFactory` with `HexGeometry`) creates the coordinate, the topology and the piece shapes, and `BoardBuilder` builds the board from them. The abstract `BaseGameRules` holds the turn skeleton as a template method.
- **The four variants:** layer 1, `src/domain/variants/hexa-lines/`, `hexa-fit/`, `hexa-sort/` and `hexa-merge/`. Each one extends `BaseGameRules` for its own cell type, for example `MergeTile` for Hexa Merge (A1), and writes its scoring policy, its state and its factory. The state of a variant is an entity: its business methods carry each change of the board, and the rules call them. It writes no piece source, progress model or capability class: those live in the engine and in `src/domain/progress/`, and the variant factory picks them (decision 3). A variant imports the engine. The engine never imports a variant.
- **Abstract Factory per variant:** layer 1. The interface `IVariantFactory` lives in `src/domain/engine/`, and each variant folder holds one implementation. It creates the whole family of statement §3.3: the rules, the piece source (`createPieceSource()`), the scoring policy and the board (`createBoard()`, with `BoardBuilder`), plus the progress model, the initial state and the optional history (decision 31). `StartGame` receives a factory and never names a variant. The cell renderer that D3 assigns to this factory cannot live here. Q8 asks where the renderer goes, and its answer can move the factory too.
- **Capability interfaces:** layer 1, `src/domain/engine/`. `IMergeable<TCell>` is the bound on the Hexa Merge cell (§3.1). `IUndoable`, `ITimed` and `IRandomSeeded` stay separate (§3.2, ISP). The engine classes `MoveHistory`, `RedoableHistory`, `LevelTimer` and `SeededPieceSource` implement them. `SeededPieceSource` is a value object, as every piece source is: a draw returns the next source and changes nothing (decision 51). The variant factory gives a game only the ones it uses, so Hexa Lines gets no `IUndoable` (decision 3). `LevelTimer` is an entity inside the `GameEngine` aggregate: its `LevelTimerId` is local, and the variant factory builds it from the `MatchId` of the game (decisions 50 and 52). The root answers for them with `undo()`, `redo()`, `canUndo()`, `canRedo()`, `offersUndo()` and `elapsedTime()`, and it hands out no capability, so no use case asks for a concrete class (decision 27, #234). `IRedoable` is our addition: Hexa Fit redoes, and Hexa Merge only undoes (§5.1.8).
- **Command and State:** layer 1, `src/domain/engine/`. `MoveCommand` wraps each move, so the history supports undo and redo: unlimited in Hexa Fit, one move in Hexa Merge (§3.3). `GamePhase` has one class per phase of a game: Playing, Resolving, Paused, GameOver and Victory (§3.3). The name avoids a clash with the `TState` type parameter. The menu belongs to the presentation layer, not to `GamePhase` (D2).
- **Game events (Observer):** the `GameEventPublisher` port lives in layer 2, `src/application/` (#233). The engine records its events at the end of a turn and tells nobody, and `ApplyMove` delivers them to the port after the turn. The events are `GameOver` and the move events `LinesCleared`, `TileMerged` and `StackCleared` (#361), and each one extends the abstract `GameEvent` (§3.3). `GameEventBus` in layer 3 implements the port. The presenters, the score display and `AudioManager`, the audio facade in layer 4, listen to it, so the engine never knows about sound or screens.
- **Use cases:** layer 2, `src/application/`. One generic set for the four variants:
  - `StartGame`, `ApplyMove`, `UndoMove`, `SaveProgress` and `SyncLeaderboard`. The game use cases keep the running engine through `GameRepository`, the repository port of the game aggregate, and `InMemoryGameRepository` in layer 3 implements it (decision 10).
  - `RedoMove`: redo in Hexa Fit (statement §5.1.8).
  - `ListLevels`: the level selector with its progress indicator and locked levels (§5.1.2). It lists the levels of a game on the chosen figure as `LevelSummary` values, each one completed, open or locked, with the stars of a completed level (#168, decision 58).
  - `Register` and `Login`: sign-up and sign-in against the backend (§5.2.1), through the `AccountGateway` port, which `ApiAccountGateway` in layer 3, `src/adapters/api/`, implements (decision 11). They write the token through the `SessionStore` port.
  - `UpdateSettings`: the mute option and the language (§5.1.10, §5.1.11), through the `SettingsStore` port, which `LocalSettingsStore` in layer 3 implements over `KeyValueStore` (decision 12).
- **Input port:** layer 2, `src/application/`, one generic interface, `UseCase<TRequest, TResponse>` (decision 9). Each use case binds it, for example `UseCase<ApplyMoveRequest<TMove>, MoveResult<TCell, TCoord>>`. The presenters depend on the interface, not on the class. Each aspect decorator implements the same interface to wrap any use case. Tests call the same interface.
- **Results and response models:** layer 2. `execute()` returns `Promise<Result<TResponse>>`: a use case reports a failure as a `Result` with a `UseCaseError` and never throws to the screen (decision 28). The response is plain data: `MoveResult` copies the cells and never carries the `Board` or the engine (decision 29).
- **Session:** the `SessionStore` port lives in layer 2. `SessionManager`, the secure token storage in layer 4, implements it. `Login` and `Register` write the token through it. The authorization aspect reads it before the sync use cases run, `SyncProgress` and `SyncLeaderboard` (§3.5). `SaveProgress` and `ListLevels` always use the local progress and need no session, so a player with no account plays and saves in the same way (D27 in [`docs/REQUIREMENTS.md`](../REQUIREMENTS.md)). `SyncProgress` pushes the local progress through a gateway port and merges the answer into `GameProgress`. #46 builds it.
- **AOP decorators:** layer 2, `src/application/`. Each decorator implements the same use case interface and wraps a use case (§3.5, A2). `RetryAspect` runs the use case again while the error of its `Result` is retryable. A decorator logs through the `Logger` port and reads the time through the `Clock` interface of the engine, because `application-imports-only-domain` forbids a logging package there. The lint rule of R-domain-determinism covers `src/application/` too, so a decorator never calls `Date.now`. The decorator passes a `UseCaseLogEntry` with the use case name, the outcome, the time and the error, never a prebuilt message. The concrete logger lives in layer 4 and writes the text (decision 37 of the class diagram).
- **Repositories:** the ports (`ProgressRepository`, `LeaderboardGateway`, `LevelRepository`) live in layer 2. The local implementations live in layer 3, `src/adapters/`. The local progress and settings use `KeyValueStore`, a driver interface of layer 3, and `BundledLevelRepository` imports the level files that the app bundles (#168). The HTTP implementations and their DTO mapper live in layer 3 too, `src/adapters/api/`, and implement the layer 2 ports over the transport interfaces of that folder (Q7, option A3). No port names a transport type. A new database or backend means a new adapter, and the use cases do not change.
- **API client:** layer 4, `src/infrastructure/api/client.ts`. `ApiClient` is the driver of the transport interfaces of layer 3, such as `HealthApi`. It uses the path types in `schema.d.ts` and the DTO types in `src/adapters/api/dto.d.ts`, which `pnpm api:generate` writes from the backend OpenAPI document. `pacts/hexablock-app-hexablock-api.json` is the contract the consumer test writes for this client. It is a test artifact, not a layer.
- **Screens:** layer 4, `app/` (Expo Router routes; the home screen, the game selector map, the game screen, the achievements screen (#188) and the level selector (#173) exist; the game screen keeps `GamePresenter` and shows `GameStage` of `src/infrastructure/ui/`, #170). Their presenters and view models live in layer 3. A screen shows each text through a key of the text catalog in layer 3, `src/adapters/texts/`: `es.ts` and `en.ts` hold one Spanish and one English entry for each key (APP-FR-11, rule R-text-catalog in `AGENTS.md`). The catalog lives in layer 3, so a presenter can read it too. Since #165 the React Native board components live in `src/infrastructure/board/` (S3-07 in #151, «Propuesta, pendiente del equipo»): `BoardView` and the `CellRenderer<TCellView>` interface. Since #170 the folder also holds `SpaceCellRenderer`, which draws a free or an occupied space. Since #174 to #177 it holds the cell renderer of each variant, `LinesCellRenderer`, `FitCellRenderer`, `SortCellRenderer` and `MergeCellRenderer`, and each one draws a free space with `SpaceCellRenderer`. `src/infrastructure/ui/` holds `MoveControls` and the move controls of each variant, `LinesControls`, `FitControls`, `SortControls` and `MergeControls`. Since #405 the controls send a plain intent and import no class of a variant, and a `MoveMapper` of each variant in layer 3 builds the domain move (decision 14 of [classes.md](classes.md)). The game registry gives each game the parts of its variant, and it has no default parts. Since #393 the screen layouts that the board components read live in layer 3, `src/adapters/board/`, by the rule of layers 3 and 4: `BoardLayout<TCoord>` with `HexLayout`, `SquareLayout` and `TriangleLayout` (#165), and `fittedCellSize()`, which fits a board to the width of the screen (#170). They convert domain values into screen numbers and import no package and no variant. Since #409 `slideWays()` (#177), which names the `Slide` of Hexa Merge, lives in `src/adapters/merge-slide-ways.ts`, next to the Merge mappers. Q8 still waits on the professor, and his answer can move the board components.
- **Presentation pattern: Model-View-Presenter (MVP).** MVP is a presentation pattern, so it works inside Clean Architecture and orders only layers 3 and 4. The view is a route in layer 4, for example `GameScreen` with `BoardView`: it shows a `GameViewModel` and forwards each input to its presenter. The presenter (`GamePresenter`) and the view model live in layer 3: the presenter calls a use case through `UseCase`, maps the plain response to the view model and gives it to the view. The view model is plain data that the presenter builds, not an object that the view binds to, so the pattern is MVP and not MVVM. The model is layers 1 and 2.
- **Dependency-injection composition root:** layer 4, `src/infrastructure/composition-root.ts` (S3-06 in #151, «Propuesta, pendiente del equipo», issue #162). It is the only module that imports from every layer. It builds the drivers and the adapters once, injects them into the use cases and wraps the use cases in the aspect decorators. Today it builds `SystemClock`, `SeededRandomSource`, `ConsoleLogger`, `SequentialMatchIds`, the one id generator of `MatchId`, and one `GameEventBus`, which goes to every `ApplyMove` (#362). Its `GameRegistry` maps each `GameId` to its variant factory and its screen parts (the state mapper, the cell renderer, the move controls and the figure layout, #170, #175), and `src/infrastructure/registered-games.ts` lists the four games. It builds one registry for each board figure, the hexagon, the square and the triangle, and each variant factory of a registry takes the `GeometryFactory` of its figure: the player chooses the figure on the home screen (APP-FR-16, #171). The root builds one `StartGame`, `ApplyMove` and `UndoMove` per game over one `InMemoryGameRepository`. `StartGame` takes the `GameFactories` port, which `LevelGameFactories` of layer 3 implements over the one `BundledLevelRepository` of the root, so one `StartGame` starts every level of its game (#172). With the local store of its drivers, `DeviceKeyValueStore`, it builds `ListAchievements` over the same level repository and `LocalProgressRepository` for the achievements screen (#188), and `ListLevels` over the same two repositories for the level selector (#173). `app/_layout.tsx` only calls it, through `CompositionRootProvider`, and the routes read it with `useCompositionRoot()`. It will create `AudioManager` and `SessionManager` once, so they have a single scope (§3.3). Q9 still waits on the professor, and his answer can move the root.

- **Q7. Where does the backend repository live?** Closed by the team on 2026-11-26 with option A3 (#404). It replaces option B of 2026-10-30.
